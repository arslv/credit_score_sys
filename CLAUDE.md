# CLAUDE.md — DIALOG Scoring

Сервис автоматических решений по заявкам на исламскую рассрочку (мурабаха, физлица).
Работает рядом с системой заказчика: забирает заявки через их API под служебным аккаунтом,
проверяет, принимает решение и записывает статус обратно.

- **Источник правды:** `docs/spec.md` (ТЗ). Перед задачей читай разделы, на которые она ссылается.
- **Задачи:** `docs/TASKS.md`. Одна сессия = одна задача. Не делай следующую без явной просьбы.
- Если ТЗ противоречит само себе — приоритет у разделов «Архитектура», «Интеграция»,
  «Жизненный цикл» и «Конвейер проверок». DDL в ТЗ — ориентир, итоговая схема живёт в миграциях.

## Стек

Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic, PostgreSQL 16, Celery + Redis,
httpx, Pydantic v2, pytest + respx, structlog. Админка: React + Vite (`frontend/`).
Всё запускается через Docker Compose.

## Команды

```bash
docker compose up -d                          # поднять всё
docker compose exec api alembic upgrade head  # миграции
docker compose exec api pytest -q             # тесты
docker compose exec api alembic revision --autogenerate -m "..."  # новая миграция
```

## Как устроен поток

- **Стадия А** — сразу после подачи, без БКИ: распознавание фото паспорта → бесплатные
  локальные проверки (паспорт, МВД, Росфинмониторинг, чёрный список) → финализация, без
  ожидания внешних сайтов. Исходы: `rejected_a` или `to_operator`. Одобрения на стадии А не
  бывает. ФНС (T16: `fns_inn`/`fns_npd`/`fns_egrip`) ставится в очередь Celery и приходит в
  карточку асинхронно, стадия его не ждёт. Федресурс убран из конвейера целиком (T16) —
  в карточке статическая подсказка «проверьте вручную на fedresurs.ru». ФССП не вызывается
  автоматически ни на одной стадии — только по ручному действию (капча решается человеком,
  см. «Словарь» → operator, `app/api/fssp.py`).
- **Стадия Б** — оператор после звонка жмёт «Рассмотреть» в их системе. Дешёвые проверки
  (полнота, шариат, лимиты) → запрос в БКИ → финансовые правила и скор.
  Исходы: `rejected_b`, `gray_zone`, `approved`. Без КИ одобрить нельзя — только серая зона;
  без пройденной проверки ФССП (заявитель и поручитель, если есть) — тоже только серая зона
  (`fssp_required_for_approval` в конфиге правил, T16).

## Непреложные правила

1. **Ничего не перезаписываем.** Таблицы `decisions`, `feature_snapshots`, `checks`,
   `status_history`, `external_snapshots`, `ocr_results`, `integration_events`,
   `ruleset_versions`, `audit_log`, `bki_reports` — только INSERT. Никаких UPDATE/DELETE
   по ним. `applications.status` — единственный изменяемый указатель; каждое его
   изменение сопровождается записью в `status_history` в той же транзакции.
   (`bki_requests_in_flight` — исключение: техническое состояние
   опроса/блокировки, а не бизнес-факт, обновляются на месте.)
   (`fssp_captcha_sessions` — тоже исключение, T16: состояние диалога
   «показали картинку капчи — оператор вводит код» (одна активная сессия на
   заявку/субъекта, новый поиск гасит предыдущую: `status=expired`) — это
   координация человека с сайтом ФССП, а не бизнес-факт; сам результат
   проверки (найдено/не найдено) пишется, как и у любого источника,
   append-only в `checks`. `fssp_post_decision_alerts`, в отличие от этой
   таблицы, — обычный append-only факт-лог, под общее правило 1.)
   (`delinquency_daily` — тоже исключение, T15: производные данные, целиком
   вычислимые из сырых платежей (`payments`), а платежи append-only — перезапись
   самой `delinquency_daily` разрешена, это пересчитываемый кэш, не факт-лог.
   `computed_at` на строке — для диагностики, не часть первичного ключа.)
2. **Бизнес-логика только в YAML-конфиге правил.** Никаких порогов, возрастов, сумм,
   сроков и названий статусов заказчика в коде. Если нужна константа — это ключ конфига.
3. **Сырые ответы внешних источников сохраняются до разбора** (`response_raw`, `payload_raw`).
4. **Каждый внешний источник реализует `SourceBase`** из `app/sources/base.py` и никогда не
   бросает исключение наружу: возвращает результат со статусом
   `ok | hit | no_data | source_unavailable | error`. Недоступный источник не роняет
   заявку и не даёт автоотказ — ведёт в ручную проверку.
5. **Деньги — `Decimal` / `numeric(14,2)`.** Никогда `float`. Исключение: признаки
   в `feature_snapshots.features` для движка правил (`app/engine/rules.py`) —
   там суммы могут быть `float`, потому что используются только для сравнения
   с порогами (`gt`/`between` и т.п.), а не как финансовая запись. Точные суммы
   в `Decimal` при этом остаются в сырых данных источника (`checks.response_raw`/
   `parsed`, правило 3) и во всех финансовых таблицах (`applications`,
   `contracts`, `payments` и т.д.) — исключение касается только этого одного
   промежуточного слоя.
6. **Время — timezone-aware UTC** (`datetime.now(timezone.utc)`, `timestamptz`).
7. **Персданные не попадают в логи приложения.** В логах только `application_id` и
   технические поля. Никаких ФИО, паспортов, телефонов, адресов. Фото в БД не хранятся —
   только ключ хранилища, хеш и метаданные.
8. **Секреты только из переменных окружения.** Никогда не коммить `.env`. Новая переменная —
   сразу в `.env.example` с пустым значением.
9. **Схема БД меняется только новой миграцией Alembic.** Существующие миграции не редактируй.
10. **В тестах нет реальных сетевых вызовов.** Внешние HTTP мокаются через respx,
    система заказчика — через заглушку `fake_partner`.
11. **Идемпотентность по `external_id`** (ID заявки в системе заказчика): повторное
    получение той же заявки в том же состоянии не запускает проверки заново.
12. **Не меняем статус, который оператор уже изменил вручную.** Перед записью статуса
    сверяем текущий; при расхождении — отмена записи и событие `conflict`.
13. **Никогда не держим открытой блокировку строки (`FOR UPDATE`) во время обращений к
    системе заказчика или внешним источникам.** Сначала фиксируем изменения и закрываем
    транзакцию, потом — внешний вызов. (Урок взаимоблокировки из T10: `write_comment`
    внутри ещё не закрытой `finalize_stage_b`-транзакции застревал на FK-проверке
    заблокированной строки `applications`.)
14. **В тестах и в коде ответ любого HTTP-вызова проверяется.** Вызов без проверки статуса
    ответа (`raise_for_status()` или явная проверка кода/тела) — ошибка, даже во
    вспомогательных функциях тестов. (Урок из T10: тестовый хелпер тихо проглотил 409 при
    недопустимом переходе статуса в fake_partner, и тест проверял не то, что думал.)

## Как работать над задачей

1. Прочитай задачу в `docs/TASKS.md` и указанные разделы `docs/spec.md`.
2. Если для задачи нужно архитектурное решение, которого нет ни в ТЗ, ни в задаче, —
   **остановись и спроси**, не решай сам.
3. Пиши тесты вместе с кодом. Задача не готова, пока `pytest` не зелёный.
4. Не трогай файлы вне рамок задачи. Не «улучшай заодно» соседний код.
5. В конце — короткий отчёт: что сделано, какие файлы изменены, какие допущения приняты,
   что осталось открытым.

## Definition of Done

- Все критерии приёмки задачи выполнены
- `pytest` зелёный, новые модули покрыты тестами
- Миграции применяются на чистую БД: `alembic upgrade head`
- `docker compose up` поднимается без ошибок
- Нет секретов и персданных в коде, логах и тестовых фикстурах
