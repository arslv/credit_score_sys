# Установка на сервере заказчика — чек-лист для сисадмина (T19)

`docker-compose.yml` в корне репозитория — конфигурация для локальной
разработки, разворачивать её как есть в бою нельзя. Боевая конфигурация —
`docker-compose.prod.yml`: без `fake_partner`, `APP_ENV=production` (жёстко),
фронтенд отдаёт `nginx` статикой, а не Vite dev-сервером, `nginx` сам
терминирует HTTPS, ежедневный бэкап Postgres и оповещения в Telegram.

## 1. Требования к серверу

- Linux x86_64, Docker Engine + Docker Compose v2 (`docker compose version` —
  не отдельный `docker-compose` v1).
- Открытые порты 80 и 443 наружу (только они — `db`/`redis`/`api`/`worker`/
  `beat` портов наружу не публикуют).
- Домен, указывающий A-записью на сервер (нужен для HTTPS-сертификата).
- Доступ в интернет наружу с сервера — нужен и для настоящих источников
  (ФНС/ФССП — публичные сайты без ключа, см. `docs/reports/T16.md`), и для
  исходящих уведомлений заказчику, и для Telegram API.
- Место на диске: фото паспортов (`storage_data`) растут с числом заявок;
  бэкапы Postgres (`BACKUP_DIR`) — `BACKUP_RETENTION_DAYS` дней дампов
  одновременно. Ориентировочно прикиньте по объёму тестового периода, точных
  цифр заранее нет.
- Если МВД/Росфинмониторинг обновляются вручную (нет автоматической
  выгрузки, см. `docs/registries.md`) — у кого-то должен быть доступ
  положить файлы в `./data/registries` на сервере.

## 2. Переменные окружения

Полный список с комментариями — `.env.example` (скопировать в `.env` рядом с
`docker-compose.prod.yml` и заполнить). **Используйте отдельный `.env` от
дев-окружения** — если по ошибке переиспользовать дев-`.env` с
`EXTERNAL_SOURCES_MODE=fake`/`OCR_PROVIDER_MODE=fixture` и т.п., сервис
сам откажется стартовать (`app/startup_guard.py`, ровно для этого случая) —
не тихий баг, но лишний повод запутаться при первом развёртывании.

Обязательные (без них `docker compose -f docker-compose.prod.yml up` сразу
откажется стартовать с понятной ошибкой — какая переменная не задана):

| Переменная | Что это |
| --- | --- |
| `POSTGRES_PASSWORD` | пароль боевой базы |
| `DOMAIN` | домен заказчика (HTTPS, nginx) |
| `ANTHROPIC_API_KEY` | распознавание паспорта (T05) |
| `PARTNER_INBOUND_TOKEN` | токен, которым заказчик подписывает вызовы к нам (`docs/integration_contract.md`) |
| `PARTNER_OUTBOUND_URL`, `PARTNER_OUTBOUND_TOKEN` | адрес и токен ИХ эндпоинта, куда мы шлём ответы |

Необязательные, но важные:

- `PARTNER_IP_ALLOWLIST` — список IP заказчика через запятую, если они его
  дадут; пусто — проверка выключена (сам токен в заголовке всё равно
  обязателен).
- `BKI_PROVIDER_MODE` — остаётся `not_configured`, пока нет договора с бюро
  (без него одобрение недостижимо в принципе, только серая зона — это
  ожидаемо на старте, не баг).
- `EXTERNAL_SOURCES_MODE=http` (по умолчанию в `docker-compose.prod.yml`) —
  настоящие ФНС/ФССП/МВД/Росфинмониторинг/чёрный список.
- `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` — см. раздел 7 ниже; пусто — без
  оповещений (сервис работает, просто некому написать при сбое).
- `BACKUP_DIR`, `BACKUP_RETENTION_DAYS`, `BACKUP_INTERVAL_SECONDS` — см.
  раздел 6.
- `CERTBOT_CONFIG_DIR` — путь к каталогу certbot на хосте, по умолчанию
  `/etc/letsencrypt` (стандартный для большинства установок certbot).

## 3. HTTPS-сертификат (certbot)

`nginx` в `docker-compose.prod.yml` ждёт сертификат по пути
`/etc/letsencrypt/live/$DOMAIN/{fullchain,privkey}.pem` **внутри своего
контейнера** — путь на хосте подставляется через `CERTBOT_CONFIG_DIR`
(весь каталог монтируется в контейнер `nginx` read-only).

Первый выпуск сертификата — вне docker compose, прямо на хосте (самый
надёжный вариант, не зависящий от того, что`nginx` ещё не поднят):

```bash
sudo apt-get install certbot   # или аналог для вашего дистрибутива
sudo certbot certonly --standalone -d <ваш-домен>
# сертификат окажется в /etc/letsencrypt/live/<ваш-домен>/
```

`--standalone` требует, чтобы порт 80 был СВОБОДЕН в момент выпуска — если
`docker-compose.prod.yml` уже запущен, на время выпуска остановите `nginx`
(`docker compose -f docker-compose.prod.yml stop nginx`) или выпускайте
сертификат до первого запуска.

Продление: `certbot renew` (можно по cron раз в день — certbot сам не
обновляет сертификат, пока не останется ~30 дней) обновляет файлы на хосте;
`nginx` подхватит новый сертификат при следующем перезапуске контейнера
(`docker compose -f docker-compose.prod.yml restart nginx`) — добавьте
`--deploy-hook` в `certbot renew`, который выполнит именно эту команду.

## 4. Первый запуск

```bash
cp .env.example .env
# заполнить .env — см. раздел 2

docker compose -f docker-compose.prod.yml up -d --build
# api сам применит миграции при старте (alembic upgrade head в command),
# frontend-build соберёт статику один раз и завершится — это нормально,
# restart: "no" у него специально.

docker compose -f docker-compose.prod.yml ps
# db/redis/api/worker/beat/nginx/backup — Up; frontend-build — Exited (0)
```

Проверка: `curl -I https://<ваш-домен>/` (фронтенд) и
`curl -I https://<ваш-домен>/api/system/status` (должен попросить вход —
401/403, не 502/504 — значит прокси до `api` достучался).

## 5. Создание первого администратора

```bash
docker compose -f docker-compose.prod.yml exec api python -m app.cli.create_admin
```

Пароль вводится через `getpass` (не эхается, не остаётся в истории шелла).
Дальше новые сотрудники заводятся уже из самой админки (роль `admin`).

## 6. Бэкап и восстановление Postgres

Сервис `backup` (`docker-compose.prod.yml`) сам делает дамп раз в
`BACKUP_INTERVAL_SECONDS` (по умолчанию раз в сутки) в `BACKUP_DIR` на хосте,
хранит `BACKUP_RETENTION_DAYS` дней (по умолчанию 14), удаляет остальное.
После каждого успешного дампа обновляется `$BACKUP_DIR/.last_success` — по
нему же проверяется алерт «бэкап не сделан» (раздел 7).

**Скопируйте `BACKUP_DIR` куда-то вне этого сервера** (rsync/scp на другую
машину или в объектное хранилище) — локальный диск не защищает от отказа
самого сервера. Это организационный вопрос на стороне заказчика, не
автоматизировано здесь.

Восстановление в боевую базу (перезаписывает её):

```bash
docker compose -f docker-compose.prod.yml exec backup \
  sh /scripts/restore_postgres.sh /backups/dialog-scoring-20261010T030000Z.dump
```

**Проверка восстановления на тестовой базе** (не трогает боевую,
рекомендуется прогонять периодически, например раз в неделю по cron на
хосте — отдельно от ежедневного бэкапа):

```bash
docker compose -f docker-compose.prod.yml exec backup \
  sh /scripts/verify_backup_restore.sh
# без аргумента — берёт самый свежий дамп; восстанавливает во временную
# базу dialog_restore_check, проверяет пару таблиц, удаляет временную базу.
```

## 7. Оповещения в Telegram

Заполните `TELEGRAM_BOT_TOKEN` (создать бота через `@BotFather` в Telegram)
и `TELEGRAM_CHAT_ID` (id чата/канала, куда бот будет писать — добавьте бота
в чат и возьмите chat_id, например через `@getidsbot` или ответ
`getUpdates` на тестовое сообщение). Пустые значения — оповещения просто не
отправляются, остальной сервис работает как обычно.

Четыре сигнала (периодическая проверка — `app/tasks/alerts.py`, раз в
`ALERTS_CHECK_INTERVAL_SECONDS`, по умолчанию 5 минут; повтор одного и того
же сообщения — не чаще раза в `ALERTS_RESEND_INTERVAL_MINUTES`, по умолчанию
час, пока сигнал не исчезнет):

- источник (МВД/Росфинмониторинг/ФНС/ФССП/БКИ/чёрный список) недоступен
  дольше `ALERTS_SOURCE_UNAVAILABLE_MINUTES` (по умолчанию 30) минут подряд;
- заявки без смены статуса дольше `ALERTS_STUCK_APPLICATIONS_MINUTES`
  (по умолчанию 60) минут;
- ответы заказчику не доставлены дольше `PARTNER_OUTBOX_STUCK_MINUTES`
  (T18, по умолчанию 30) минут;
- бэкап не завершался успешно дольше `ALERTS_BACKUP_MAX_AGE_HOURS`
  (по умолчанию 26 часов — чуть больше суток, запас на разовую задержку).

Экран состояния системы в админке (`/api/system/status`, роль `admin`) —
для риск-менеджера, служит другой цели (T12) и не заменяет эти оповещения:
Telegram-алерт приходит дежурному, даже если никто в этот момент не смотрит
в админку.

## 8. Обновление версии

```bash
git pull
docker compose -f docker-compose.prod.yml up -d --build
# alembic upgrade head выполнится сам при старте api; frontend-build
# пересоберёт статику заново.
```

Миграции применяются только вперёд (правило 9 CLAUDE.md — существующие не
редактируются). Откат версии кода при уже применённой новой миграции не
поддерживается этим процессом — потребовалось бы восстановление из бэкапа.

## 9. Обратный прокси и адрес клиента (T12)

Блокировка входа по IP (`app/security/rate_limit.py`) считает попытки по
адресу, который видит приложение. `docker-compose.prod.yml` уже настраивает
это корректно «из коробки»:

- `nginx` сидит на фиксированном внутреннем адресе (`NGINX_INTERNAL_IP`,
  по умолчанию `172.28.0.10` — задан явно, не маска подсети и не `*`);
- `uvicorn` запущен с `--proxy-headers --forwarded-allow-ips
  $NGINX_INTERNAL_IP` — доверяет `X-Forwarded-For` только от этого адреса;
- `deploy/nginx/nginx.conf.template` **перезаписывает** `X-Forwarded-For`
  значением `$remote_addr`, а не дописывает в него
  (`proxy_set_header X-Forwarded-For $remote_addr;`) — иначе клиент мог бы
  приписать в заголовок собственное значение перед настоящим.

Если меняете топологию (свой внешний балансировщик перед `nginx` и т.п.) —
пересчитайте обе стороны этой цепочки заново, иначе блокировка по IP
перестанет отличать пользователей.

Проверка после разворачивания: залогиниться с ошибкой несколько раз с
реальной машины и с другой — счётчики (`login_attempts:ip:*` в Redis)
должны быть разными, не общими.

## 10. Один origin для админки и API — CORS не настроен (T13)

`CORSMiddleware` в `app/main.py` намеренно отсутствует — админка и API
всегда на одном origin. В бою это обеспечивает `nginx`:
`/api/*` проксируется на `api:8000`, всё остальное отдаёт собранную статику
фронтенда — с того же домена, без отдельного поддомена/порта. Если
когда-нибудь понадобится админка на другом origin — CORS придётся вернуть
явно (`allow_origins` конкретным списком + `allow_credentials=True`),
никогда `allow_origins=["*"]` вместе с куками сессии.

## 11. DNS: statusnpd.nalog.ru (T16)

Перед вводом в бой явно проверьте (`getent hosts statusnpd.nalog.ru` или
аналог на сервере), что резолвер сервера резолвит эту запись — в одном из
окружений разработки эта конкретная запись не резолвилась системным
резолвером при рабочем публичном DNS, хотя остальные поддомены `nalog.ru`
резолвились нормально (см. `docs/reports/T16.md`). Если не резолвится —
это настройка DNS/сети на стороне инфраструктуры сервера, не задача этого
сервиса подставлять свой резолвер.
