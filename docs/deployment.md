# Боевая конфигурация — требования (T11)

`docker-compose.yml` в корне репозитория — конфигурация для локальной разработки.
Разворачивать её как есть у заказчика нельзя.

## fake_partner не едет в бой

`fake_partner/` — заглушка системы заказчика для дев-окружения и тестов
(служебные эндпоинты `/_test/*`: создание заявок в обход формы, принудительная
смена статуса, сброс состояния). В боевом окружении заказчика этот сервис не
поднимается вообще — вместо него используется их настоящее API.

Требования к будущей боевой compose-конфигурации (отдельный файл, например
`docker-compose.prod.yml` — пока не создан, эта задача не входила в объём T11):

- Без сервиса `fake_partner` и без его образа.
- `PARTNER_BASE_URL` указывает на настоящий API заказчика.
- `APP_ENV=production` (по умолчанию в коде, см. `app/config.py` и
  `app/startup_guard.py`) — сервис (api, worker, beat) сам откажется
  стартовать, если `OCR_PROVIDER_MODE`/`BKI_PROVIDER_MODE`/`EXTERNAL_SOURCES_MODE`
  окажутся в fake/fixture-режиме.
- Секреты (`ANTHROPIC_API_KEY`, ключи ФССП/ФНС и т.п.) — из настоящего
  секрет-хранилища окружения, не из `.env`, закоммиченного в репозиторий
  (правило 8 CLAUDE.md).

## Обратный прокси и адрес клиента (T12)

В бою перед `api` будет обратный прокси (nginx/что у заказчика). Блокировка
входа по IP (`app/security/rate_limit.py`) считает попытки по адресу, который
видит приложение (`request.client.host`) — без настройки это будет адрес самого
прокси, ОДИН И ТОТ ЖЕ для всех пользователей: один злоумышленник, подбирающий
пароль, заблокирует вход всем остальным с этого прокси.

Обязательно при разворачивании:

- `uvicorn` запускать с `--proxy-headers --forwarded-allow-ips <адрес прокси>`,
  указав именно адрес прокси (не `*`) — иначе `uvicorn` примет `X-Forwarded-For`
  от кого угодно, и внешний клиент сможет подставить в этот заголовок чужой или
  произвольный адрес, обходя блокировку или подставляя под неё постороннего.
- Сам прокси должен **перезаписывать** `X-Forwarded-For` значением реального
  адреса клиента, а не дописывать в него (`proxy_set_header X-Forwarded-For
  $remote_addr;` в nginx, не `$proxy_add_x_forwarded_for`) — иначе клиент может
  приписать в заголовок собственное значение перед настоящим, и приложение (или
  следующий прокси в цепочке) возьмёт чужой адрес.
- Проверка после разворачивания: залогиниться с ошибкой несколько раз с реальной
  машины и с другой — счётчики (`login_attempts:ip:*` в Redis) должны быть
  разными, не общими.

## Один origin для админки и API — CORS не настроен (T13)

Админка (React) и API (`api`) в браузере всегда на одном origin — CORS
намеренно не настроен в `app/main.py` (`CORSMiddleware` убран). В dev это
делает Vite (`frontend/vite.config.ts`: прокси `/api` на `api:8000` внутри
docker-сети). В бою тот же принцип должен обеспечивать nginx (или что
использует заказчик) перед сервисом:

- статика собранного фронтенда (`npm run build` в `frontend/`) отдаётся с
  корня;
- `/api/*` проксируется на бэкенд (`proxy_pass http://api:8000;` в терминах
  nginx) — с того же origin, что и статика, без отдельного поддомена/порта.

Если когда-нибудь понадобится админка на ДРУГОМ origin (например, отдельный
поддомен без общего прокси), CORS придётся вернуть явно — с точным списком
разрешённых origin'ов (`allow_origins`) и `allow_credentials=True`; никогда не
с `allow_origins=["*"]` вместе с куками сессии.

## Secure-кука сессии (T13)

`COOKIE_SECURE` — по умолчанию `true` (см. `app/config.py`); сервис
отказывается стартовать в `APP_ENV=production` со значением `false`
(`app/startup_guard.py`). Соединение с админкой — только по HTTPS (ТЗ,
«Требования по персональным данным»), поэтому в бою `COOKIE_SECURE` не
трогать. Значение `false` допустимо только в dev-`docker-compose.yml` — там
это нужно, потому что Secure-кука на `http://localhost` ведёт себя
по-разному в браузерах (Safari может не сохранить её вовсе).

## DNS: statusnpd.nalog.ru (T16, разведка перед подключением ФНС)

В окружении разработки (эта сессия) системный резолвер не резолвит
`statusnpd.nalog.ru` (`Could not resolve host`), хотя через публичный DNS
(`8.8.8.8`) домен резолвится нормально (CNAME на `statusnpd.gi.nalog.ru`) и
сам сервис отвечает (`405` на GET — ждёт POST, как и ожидалось). Остальные
поддомены `nalog.ru`, использованные в T16 (`service.nalog.ru`,
`egrul.nalog.ru`), резолвятся обычным резолвером без проблем — это точечная
особенность именно одной записи, не общая геоблокировка.

**В коде/конфиге никакого захардкоженного IP или альтернативного DNS не
добавлено** — `app/sources/fns.py` обращается к `statusnpd.nalog.ru` по
имени, как и к остальным источникам, и полагается на системный резолвер
хоста. Перед вводом в бой на сервере заказчика нужно явно проверить
(`getent hosts statusnpd.nalog.ru` или аналог), что резолвер сервера эту
запись резолвит — если нет, это настройка DNS/сети на стороне инфраструктуры
заказчика, не задача этого сервиса подставлять свой резолвер.
