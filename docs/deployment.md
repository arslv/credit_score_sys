# Боевая конфигурация — требования (T11)

`docker-compose.yml` в корне репозитория — конфигурация для локальной разработки.
Разворачивать её как есть у заказчика нельзя.

## fake_partner не едет в бой

`fake_partner/` — заглушка системы заказчика для дев-окружения и тестов
(служебные эндпоинты `/_test/*`: создание заявок в обход формы, принудительная
смена статуса, сброс состояния). В боевом окружении заказчика этот сервис не
поднимается вообще — вместо него используется их настоящее API.

Требования к будущей боевой compose-конфигурации (отдельный файл, например
`docker-compose.prod.yml` — пока не создан, эта задача не входила в объём T11):

- Без сервиса `fake_partner` и без его образа.
- `PARTNER_BASE_URL` указывает на настоящий API заказчика.
- `APP_ENV=production` (по умолчанию в коде, см. `app/config.py` и
  `app/startup_guard.py`) — сервис (api, worker, beat) сам откажется
  стартовать, если `OCR_PROVIDER_MODE`/`BKI_PROVIDER_MODE`/`EXTERNAL_SOURCES_MODE`
  окажутся в fake/fixture-режиме.
- Секреты (`ANTHROPIC_API_KEY`, ключи ФССП/ФНС и т.п.) — из настоящего
  секрет-хранилища окружения, не из `.env`, закоммиченного в репозиторий
  (правило 8 CLAUDE.md).

## Обратный прокси и адрес клиента (T12)

В бою перед `api` будет обратный прокси (nginx/что у заказчика). Блокировка
входа по IP (`app/security/rate_limit.py`) считает попытки по адресу, который
видит приложение (`request.client.host`) — без настройки это будет адрес самого
прокси, ОДИН И ТОТ ЖЕ для всех пользователей: один злоумышленник, подбирающий
пароль, заблокирует вход всем остальным с этого прокси.

Обязательно при разворачивании:

- `uvicorn` запускать с `--proxy-headers --forwarded-allow-ips <адрес прокси>`,
  указав именно адрес прокси (не `*`) — иначе `uvicorn` примет `X-Forwarded-For`
  от кого угодно, и внешний клиент сможет подставить в этот заголовок чужой или
  произвольный адрес, обходя блокировку или подставляя под неё постороннего.
- Сам прокси должен **перезаписывать** `X-Forwarded-For` значением реального
  адреса клиента, а не дописывать в него (`proxy_set_header X-Forwarded-For
  $remote_addr;` в nginx, не `$proxy_add_x_forwarded_for`) — иначе клиент может
  приписать в заголовок собственное значение перед настоящим, и приложение (или
  следующий прокси в цепочке) возьмёт чужой адрес.
- Проверка после разворачивания: залогиниться с ошибкой несколько раз с реальной
  машины и с другой — счётчики (`login_attempts:ip:*` в Redis) должны быть
  разными, не общими.
