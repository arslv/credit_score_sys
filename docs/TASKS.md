## T05. Распознавание фото паспорта

**Разделы ТЗ:** «Архитектура» (модуль распознавания), «Конвейер проверок» (шаг 1), «Анкета».

**Сделать**
- Интерфейс `OcrProvider` и реализация через Anthropic API (Messages, изображения в base64,
  структурированный ответ через tool use с JSON-схемой). Модель и ключ — из env
  (`ANTHROPIC_API_KEY`, `OCR_MODEL`)
- В провайдер отправляются **только** разворот паспорта и страница регистрации. Селфи не отправляется
- Схема ответа: поля паспорта и прописки из раздела «Распознаётся с фото», у каждого поля
  значение и уверенность 0–1; флаги `unreadable`, `cropped`, `possible_edit`
- Нормализация: даты в ISO, серия 4 цифры, номер 6 цифр, код подразделения `XXX-XXX`
- Сверка ФИО с формой (нечёткая, с допуском на опечатки) — флаг при расхождении
- Сохранение в `ocr_results` (сырой ответ + разобранные поля)
- Порог уверенности ключевых полей из конфига; ниже порога → `ocr_failed`
- Фейковый провайдер для тестов, возвращающий заранее заданный JSON

**Критерии приёмки**
- Тесты на нормализацию и на порог уверенности через фейковый провайдер
- Ручной прогон на синтетических фото из заглушки даёт осмысленные поля
- В логах нет распознанных персданных

**Вне рамок:** проверки по распознанным данным.

## T06. Движок правил и конфиг

**Разделы ТЗ:** «Конфиг правил и пороги».

Самая важная задача. Делать тщательнее всего.

**Сделать**
- Загрузка YAML, валидация через Pydantic-схему (опечатка в ключе — ошибка, а не молчание)
- Версии в `ruleset_versions`; активная — по `effective_from`
- Операторы: `eq, ne, lt, lte, gt, gte, between, in, not_in, is_null`
- Доступ к полям по пути (`checks.mvd.status`, `features.pti`)
- Секции `hard_stops`, `stage_b_pre_bki`, `soft_rules`, `limits`, `score_thresholds`, `matrix`
- Результат: исход, код причины, список сработавших правил **с фактическими значениями и порогами**
- Отсутствующее поле: правило не срабатывает и попадает в список `missing_fields`
- Движок — чистая функция: на вход признаки + конфиг, на выход решение. Без БД и сети

**Критерии приёмки**
- Тест на каждый оператор, включая граничные значения
- Тест на `matrix`: переопределение порога по условию
- Тест: невалидный YAML отклоняется с понятной ошибкой
- Тест: одно и то же на входе → одно и то же на выходе

**Вне рамок:** источники данных, симуляция (T14).

## T11. БКИ: интерфейс, заглушка, финансовые правила

## T12. API админки: авторизация, роли, аудит

**Разделы ТЗ:** «Роли, доступ и персданные», «Админка».

**Сделать**

- Роли из ТЗ, проверка прав на каждом эндпоинте
- Эндпоинты: список и карточка заявки, клиенты, договоры, справочники, сотрудники,

- Роль `viewer` получает обезличенные данные
- Снятие заморозки при санкциях (T09, `decisions.freeze`) — только ролью
  комплаенса (в таблице ролей ТЗ такой роли пока нет, нужно завести при
  реализации задачи). Снятие — НОВАЯ запись, не UPDATE/DELETE по `decisions`

  паспорта снова проходят полный набор проверок стадии А с нуля — не получают
  автоматический отказ по старому решению и не получают автоматическое
  одобрение, просто перестают попадать под ранний выход в
  `app/engine/freeze.py`.

**Критерии приёмки**
- Тест на каждую роль: разрешённое работает, запрещённое → 403
- Тест: просмотр фото пишет аудит
- Тест: `viewer` не видит ФИО и паспорт
- Тест: снятие заморозки без причины отклоняется
- Тест: снятие заморозки не роняет и не меняет старые строки `decisions`
- Тест: заявка того же паспорта после снятия заморозки проходит проверки стадии А заново

## T14. Редактор правил и симуляция

**Разделы ТЗ:** «Конфиг» (версионирование, обязательная симуляция), «Админка» (правила и пороги).
