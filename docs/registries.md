# Обновление реестров МВД и Росфинмониторинга

Автоматической выгрузки нет ни у одного из источников: форма МВД защищена
капчей, у Росфинмониторинга (fedsfm.ru) нет документированного API. Поэтому файлы
на сервер кладёт человек — вручную или полуавтоматическим скриптом, который сам
не входит в этот репозиторий.

## Что и куда класть

Синхронизатор (`app/registries/`) читает файлы из каталога, заданного
`REGISTRIES_DIR` (по умолчанию `/data/registries`, в docker compose — bind mount
`./data/registries` с хоста). Формат — CSV, наш собственный (см.
`app/registries/parsers.py`), потому что официального публичного формата нет:

| Файл | Колонки |
| --- | --- |
| `mvd_invalid_passports.csv` | `passport_series,passport_number` |
| `rosfinmon_sanctions.csv` | `list_type,full_name,birth_date` (`birth_date` может быть пустым; `list_type` — `te`\|`fromu`\|`mvk`\|`un`) |

## Процесс обновления

1. Оператор скачивает актуальную выгрузку с сайта МВД (список недействительных
   паспортов) и с fedsfm.ru (все четыре перечня — Т/Э, ФРОМУ, МВК, ООН),
   конвертирует в CSV нужного вида.
2. Кладёт файл на сервер в `REGISTRIES_DIR` под ожидаемым именем — `scp`/`rsync`
   на хост, где смонтирован `./data/registries` (bind mount, не именованный
   volume — именно чтобы к каталогу был обычный файловый доступ с хоста, без
   входа в контейнер).
3. Файл **замещает** предыдущий с тем же именем — синхронизатор всегда читает
   файл целиком заново, не дописывает.
4. Периодическая задача Celery (`registries.sync_all`, интервал
   `REGISTRIES_SYNC_INTERVAL_SECONDS`, по умолчанию раз в сутки — как источники и
   публикуют обновления) забирает файл и атомарно подменяет таблицу в БД. Ничего
   вручную запускать не нужно, если файл лёг до срабатывания задачи.
5. Результат — строка в `registry_sync_log` (`ok`/`error`), а свежесть каждого
   реестра видна в `GET /health` (поле `registries`).

## Как узнать, что реестр устарел

`GET /health` проверяет `registry_sync_log` и возвращает `"status": "degraded"`
(HTTP 200, не 503 — устаревший реестр не роняет сервис и не блокирует заявки, они
просто не получают автоотказ по этому источнику, см. `is_registry_stale`) плюс
детали по каждому реестру:

```json
{
  "status": "degraded",
  "checks": {"database": "ok", "redis": "ok"},
  "registries": {"mvd_invalid_passports": "stale", "rosfinmon_sanctions": "ok"}
}
```

Порог — `sources.registries.max_staleness_days` в активном конфиге правил.

**Открытый вопрос:** сам факт `degraded` в `/health` — это ещё не алерт, который
кто-то увидит сам по себе. Реальная доставка (почта, чат, пейджинг) требует
подключить внешний мониторинг (Pingdom/UptimeRobot/Prometheus blackbox exporter
и т.п.), настроенный на опрос этого эндпоинта и реакцию на `status != "ok"`. Ни
такого мониторинга, ни учётных данных для канала оповещения в проекте пока нет —
это отдельная организационная задача, не техническая доработка кода.
