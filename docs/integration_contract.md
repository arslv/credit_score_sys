# Контракт интеграции DIALOG Scoring ↔ CRM

Обмен идёт по API, которое прислала CRM: [`crm_api.yml`](./crm_api.yml)
(их файл без изменений). Здесь — как его реализуем мы, что требуется от CRM и
какие необязательные поля мы готовы принимать сверх их схемы.

Коротко: CRM шлёт нам новую заявку (`/new-order`) и анкету после звонка
(`/scoring`). Мы в ответ шлём распознанный паспорт (`passport-result`) и
решение (`result`) на их адреса.

## Общее

- Везде JSON, `Content-Type: application/json`, только HTTPS в проде.
- Авторизация в обе стороны — статичный токен `Authorization: Bearer <токен>`,
  разные значения для теста и боя:
  - **наш токен для CRM** (их запросы к нам) — выдаём мы, у нас
    `PARTNER_INBOUND_TOKEN`;
  - **их токен для нас** (наши запросы к ним) — выдают они, у нас
    `PARTNER_OUTBOUND_TOKEN`.
- **Allowlist IP обязателен**: CRM присылает адреса, с которых будет к нам
  ходить. Запрос с другого адреса — `403`.
- Лимит тела запроса — 25 МБ (`413` с понятным текстом, если больше).
- Повторы безопасны (идемпотентность по номеру заявки, правило 11 CLAUDE.md):
  - `/new-order` с уже известным `orderId` — `200`, ничего не создаём заново;
  - `/scoring` с тем же телом — `200`, ничего не запускаем заново; с
    изменённым телом (оператор поправил анкету) — новая стадия Б.
- Отвечаем `200 {"status": "accepted"}` сразу и обрабатываем асинхронно:
  результат приходит нашим запросом на их адрес.

## 1. CRM → нам: новая заявка

`POST https://<наш хост>/api/v1/crm/new-order` — `NewOrderNotification`.

```json
{
  "orderId": 10492,
  "lastName": "Иванов",
  "firstName": "Иван",
  "fatherName": "Иванович",
  "phone": "+79991234567",
  "passportPhotos": ["iVBORw0KGgoAAAANSUhEUgAA...", "https://photos.crm.ru/tmp/9f2a-reg.jpg"]
}
```

| Поле | Как мы его понимаем |
| --- | --- |
| `orderId` | Номер заявки в CRM. Постоянный: по нему же придёт `/scoring` и по нему мы отвечаем. |
| `passportPhotos` | **Ровно в таком порядке: `[0]` — разворот с фото, `[1]` — прописка.** Меньше двух — `422`. Остальные (если пришлют) не используем, селфи не нужно. Каждый элемент — base64 (можно с префиксом `data:image/jpeg;base64,`) или ссылка `https://`. |

Требования к фото:

- только JPEG или PNG (проверяем байты файла) — иначе `415`;
- не больше 8 МБ на фото — иначе `413`;
- ссылка — только `https://` и только с хостов, которые CRM назовёт заранее
  (`PARTNER_PHOTO_HOSTS`); ждём ответ не дольше 10 секунд, редиректы не
  выполняем. Пока хосты не согласованы — только base64.

## 2. CRM → нам: анкета после звонка («Рассмотреть»)

`POST https://<наш хост>/api/v1/crm/scoring` — `ScoringRequest`. `orderId`
должен быть уже известен из `/new-order`, иначе `404`.

```json
{
  "orderId": 10492,
  "productCategory": "household_appliances",
  "price": 60000,
  "firstPayment": 6000,
  "period": 12,
  "clientIncome": 90000,
  "otherCreditPayments": 15000,
  "bkiConsent": true,
  "guarantors": []
}
```

| Поле | Что мы с ним делаем |
| --- | --- |
| `productCategory` | Код категории товара — шариатский фильтр и лимиты. **Нужен список кодов CRM**, чтобы сопоставить с нашим справочником категорий. |
| `price`, `firstPayment`, `period` | Цена, первый взнос (₽), срок (мес.). Сумма рассрочки = цена − взнос. |
| `clientIncome` | Доход клиента в месяц со слов клиента — для долговой нагрузки (ПДН). |
| `otherCreditPayments` | Платежи по другим кредитам в месяц со слов клиента. |
| `bkiConsent` | Согласие на запрос в БКИ. Время согласия — момент получения запроса. Без согласия одобрить нельзя — только «решение за оператором». |
| `guarantors` | Поручители. Проверяем **только первого**. Без даты рождения и паспорта поручителя проверить его нельзя (перечни, ФССП, БКИ) — см. расширения ниже. |

### Необязательные поля сверх их схемы (расширения)

В `crm_api.yml` этих полей нет. Если CRM сможет их присылать — примем и
используем; если нет — работаем без них (последствия — в таблице).

| Поле | Без него |
| --- | --- |
| `employment` — `{"type": "employed"\|"self_employed"\|"unemployed"\|…, "employer": "…", "position": "…"}` | Не обязательна (решение владельца 02.11.2026). Критерии рейтинга клиента по работе — «нет данных». |
| `monthlyPayment` — платёж по рассрочке в месяц по графику CRM, с наценкой | Считаем сами по тарифу: (цена − взнос) × (1 + наценка) / срок. Если тариф неизвестен — ПДН «не вычислимо», автоматически не одобрить. |
| `tariff` — код тарифа (`standard` — Базовый, `advantageous` — Выгодный, `repeat_client` — Постоянному клиенту) | Тарифами не пользуемся (решение владельца 02.11.2026): считаем по `default_tariff` из правил («Базовый»). |
| `goodsName` — название товара | В карточке вместо названия — категория. |
| `contacts` — `[{"name", "phone", "relation": "parent"\|"sibling"\|"relative"\|"spouse"\|"friend"\|"colleague"\|"other"}]` | Критерий рейтинга «Контакты» — «нет данных». |
| `guarantors[].birthDate`, `passportSeries`, `passportNumber`, `issuedDate`, `registrationAddress` | Поручителя не проверяем; одобрение «под поручителя» не получится. |
| `applicant` — паспорт заявителя (`lastName`, `firstName`, `fatherName`, `birthDate`, `passportSeries`, `passportNumber`, `issuedDate`, `issuedBy`, `divisionCode`, `registrationAddress`) | Нужно **только если у нас выключено распознавание фото**: тогда заявка ждёт паспорт, и `/scoring` без него — `422`. Пока распознавание включено — не нужно. |

## 3. Мы → CRM

Базовый адрес их API — `PARTNER_OUTBOUND_URL` (без пути). Мы добавляем пути
из `crm_api.yml`.

### 3.1. Распознанный паспорт — `POST {база}/v1/integration/scoring/passport-result`

**Пока не отправляем** (решение владельца 02.11.2026): включается
`PARTNER_SEND_PASSPORT_RESULT=true`. Тогда — сразу после распознавания фото,
не дожидаясь решения.

```json
{
  "orderId": 10492,
  "lastName": "Иванов",
  "firstName": "Иван",
  "fatherName": "Иванович",
  "birthDate": "1990-05-14",
  "passportSeries": "8215",
  "passportNumber": "123456",
  "issuedBy": "МВД по Республике Дагестан",
  "issuedDate": "2015-03-10",
  "divisionCode": "050-001",
  "registrationAddress": "г. Махачкала, ул. Примерная, д. 1"
}
```

Поле, которое не распознали, приходит `null`.

### 3.2. Решение — `POST {база}/v1/integration/scoring/result`

После стадии А и после стадии Б.

```json
{
  "orderId": 10492,
  "status": "approved",
  "score": 742,
  "reason": "Одобрено: сумма 54000.00, срок 12 мес., тариф standard, первый взнос 6000.00."
}
```

| Поле | Комментарий |
| --- | --- |
| `status` | Статус в словаре CRM. Соответствие наших исходов их статусам — в `config/status_mapping.yaml`. **Нужен список статусов CRM** — пока стоят наши условные `rejected`, `on_call`, `manual_decision`, `approved`. |
| `score` | Балл БКИ, если он есть (на стадии А — `null`). |
| `reason` | Причина человеческим текстом для оператора, без служебных кодов. Предложение другого тарифа — тоже здесь, отдельной строкой (отдельного адреса для комментариев у CRM нет). |

Ответы CRM, которые мы понимаем:

- `2xx` — принято;
- `5xx` или нет ответа — повторим позже с растущей паузой, ничего не теряется;
- `4xx` — тоже повторяем (причина видна в журнале), пока не примут;
- `409 {"current_status": "...", "reason": "..."}` — **в их API этого нет**,
  но если CRM начнёт так отвечать, когда оператор уже сменил статус вручную,
  мы не будем перезаписывать и покажем расхождение в карточке.
