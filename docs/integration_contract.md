# Контракт интеграции DIALOG Scoring ↔ система заказчика (T18)

Этот документ — для программистов на стороне заказчика. Короткая версия: вы
шлёте нам заявку, когда она появляется на сайте, и шлёте нам анкету, когда
оператор нажимает «Принять на рассмотрение». Мы в ответ шлёте вам статус и
распознанные данные на один ваш эндпоинт, когда они готовы.

Машиночитаемая версия того же контракта — [`openapi.yaml`](./openapi.yaml)
(только наша сторона — два входящих эндпоинта; формат вашего эндпоинта описан
ниже текстом, так как это не наш сервис).

## Общее

- Везде JSON, `Content-Type: application/json`.
- Авторизация — статичный токен в заголовке `Authorization: Bearer <токен>`,
  **в обе стороны**, разные значения для тестового и боевого контуров.
  Токен, которым подписаны ваши запросы к нам — у вас в переменной окружения
  (мы вам его выдаём). Токен, которым подписаны наши запросы к вам — тоже у
  вас, вы нам его выдаёте, мы кладём в свою переменную окружения.
- Только HTTPS в проде.
- **Allowlist IP обязателен** (T21): пришлите список адресов, с которых ваши
  серверы будут к нам стучаться. Без него наш боевой контур не запускается;
  запрос с другого адреса — `403`.
- **Лимит тела любого запроса — 25 МБ** (одинаково на нашем прокси и в
  приложении). Больше — `413` с JSON `{"detail": "тело запроса больше
  допустимых 25 МБ — …"}`, такой запрос повторять бессмысленно: уменьшите фото.
- Любой запрос с вашей стороны идемпотентен по `event_id`: если вы прислали
  тот же `event_id` повторно (например, у вас сработал таймаут и вы
  повторили запрос, а наш ответ на самом деле дошёл) — мы просто отвечаем
  `202` второй раз, ничего не создаём и не запускаем заново.
- Мы отвечаем `202 Accepted` сразу и обрабатываем асинхронно. Если нужно
  узнать результат раньше, чем мы сами вам его пришлём — такого эндпоинта
  опроса у нас нет, мы сами вам напишем, когда он будет готов.

## 1. Новая заявка с сайта → нам

`POST /api/v1/partner/applications`

Шлите, как только клиент заполнил форму на сайте и прикрепил оба фото
паспорта. **Селфи нам не нужно и не нужно присылать.**

Фото можно передать либо base64 в теле, либо временной ссылкой (HTTPS,
доступной нам без авторизации, живущей хотя бы несколько минут — мы скачаем
сразу после получения запроса).

```json
{
  "external_id": "APP-10492",
  "event_id": "2f5a35b1-9e2e-4d3b-8a1a-2a6a9e9b7b21",
  "last_name": "Иванов",
  "first_name": "Иван",
  "middle_name": "Иванович",
  "phone": "+79991234567",
  "photos": {
    "passport_main": { "base64": "iVBORw0KGgoAAAANSUhEUgAA..." },
    "passport_reg": { "url": "https://cdn.example.com/tmp/9f2a-reg.jpg" }
  }
}
```

Поля:

| Поле | Тип | Обязательно | Комментарий |
| --- | --- | --- | --- |
| `external_id` | строка | да | ID заявки у вас. Постоянный — по нему мы узнаём повторную заявку того же клиента и дальнейшие `/review` по этой же заявке. |
| `event_id` | строка (UUID или любая уникальная строка) | да | Идентификатор именно этого запроса, для защиты от повторной обработки при ретрае. Новый на каждый HTTP-запрос, не на заявку. |
| `last_name`, `first_name` | строка | да | Как ввёл клиент в форме. |
| `middle_name` | строка | нет | — |
| `phone` | строка | да | — |
| `photos.passport_main` | объект `{url}` или `{base64}` | да | Разворот паспорта (фото с ФИО/серией/номером). |
| `photos.passport_reg` | объект `{url}` или `{base64}` | да | Страница с пропиской. |

### Требования к фото (T21)

- **Формат — только JPEG или PNG.** Проверяем и заголовок ответа
  (`Content-Type: image/jpeg` или `image/png`), и сами байты файла.
  Другой формат — `415`.
- **Размер — не больше 8 МБ на одно фото** (после декодирования base64).
  Больше — `413`. Два фото в base64 по 8 МБ укладываются в общий лимит тела
  25 МБ.
- **Ссылка (`url`) — только `https://` и только с хостов, которые вы нам
  заранее назовёте** (точное имя хоста, например `photos.ваш-домен.ru`;
  поддомены не подразумеваются — каждый пришлите отдельно). Ссылка на
  другой хост или по `http://` — `422`, и мы по ней даже не ходим. Пока
  список хостов не согласован, шлите фото только в `base64`.
- По ссылке мы ждём ответа **не дольше 10 секунд**, **редиректы не
  выполняем** (ссылка должна сразу отдавать файл с кодом `200`), ссылка
  должна жить хотя бы несколько минут после отправки запроса.

Ответ: `202 {"status": "accepted"}`.

Ошибки: `401` — неверный или отсутствующий токен; `403` — запрос не с
адреса из allowlist; `413` — фото больше 8 МБ или всё тело больше 25 МБ;
`415` — фото не JPEG/PNG; `422` — не хватает поля, ссылка на фото не с
согласованного хоста или не https, фото не удалось скачать или разобрать
(тело с описанием). `409` здесь не бывает, конфликтовать не с чем — заявка
только создаётся.

## 2. «Принять на рассмотрение» → нам

`POST /api/v1/partner/review`

Шлите, когда оператор у вас нажал кнопку «Принять на рассмотрение» после
звонка клиенту. `external_id` должен быть уже известен нам (из шага 1) —
иначе `404`.

```json
{
  "external_id": "APP-10492",
  "event_id": "7c1e2b3a-5566-4a1a-9f0e-1234567890ab",
  "status": "on_review",
  "deal": {
    "goods_category_code": "household_appliances",
    "goods_name": "Стиральная машина",
    "goods_price": 60000,
    "down_payment": 6000,
    "term_months": 12,
    "tariff": "standard",
    "monthly_payment": 4950
  },
  "employment": { "type": "employed" },
  "income": { "declared_monthly": 90000 },
  "obligations": { "monthly_payment_total": 15000 },
  "bki_consent": { "given": true, "at": "2026-10-10T09:15:00+00:00" },
  "guarantor": null
}
```

Поля:

| Поле | Тип | Обязательно | Комментарий |
| --- | --- | --- | --- |
| `external_id`, `event_id` | строка | да | Как в п.1. |
| `status` | строка | да | Ваш статус заявки в момент отправки — мы вернём его вам же как `prev_status` в решении, чтобы вы могли отличить «мы ответили на то состояние» от более позднего. |
| `deal.goods_category_code` | строка | нет | Код категории товара (шариат-фильтр). |
| `deal.goods_name` | строка | нет | Человекочитаемое название товара. |
| `deal.goods_price` | число | да | Цена товара, рубли. |
| `deal.down_payment` | число | да | Первый взнос, рубли. |
| `deal.term_months` | целое | да | Срок рассрочки, месяцев. |
| `deal.tariff` | строка | нет | Код тарифа, если у вас есть свой выбор тарифа на сайте. |
| `deal.monthly_payment` | число > 0 | **да, для расчёта долговой нагрузки** (T21) | Ежемесячный платёж клиента по этой рассрочке по вашему графику — с наценкой, рубли. Входит в долговую нагрузку (ПДН): (платежи по другим кредитам + этот платёж) / доход. Если не пришлёте — посчитаем сами по тарифу (цена − взнос) × (1 + наценка тарифа) / срок, но это приблизительно; если и тариф нам не известен — ПДН «не вычислимо», одобрить автоматически будет нельзя. |
| `employment` | объект | да (непустой) | Занятость клиента — минимум `{"type": "employed"\|"self_employed"\|"unemployed"\|...}`. Без этого раздела посчитать долговую нагрузку нельзя — вернём `on_call` с пометкой «не хватает данных». |
| `income` | объект | да (непустой) | Доход — минимум `{"declared_monthly": <число>}`. |
| `obligations` | объект | нет | Платежи по другим кредитам со слов клиента, например `{"monthly_payment_total": <число>}`. Пустой объект — считаем, что обязательств нет. |
| `bki_consent.given` | bool | да | Согласие клиента на запрос в БКИ. |
| `bki_consent.at` | дата-время ISO 8601 | нет | Когда дано согласие. Если `given=true` и `at` не прислан — берём момент получения запроса. |
| `guarantor` | объект или `null` | нет | Если есть поручитель: `last_name`, `first_name`, `middle_name`, `birth_date`, `passport_series`, `passport_number`, `issue_date`, `registration_address`, `phone` — все опциональны внутри объекта, но чем полнее, тем раньше пройдут проверки поручителя. |

Ответ: `202 {"status": "accepted"}`.

Ошибки: `401`; `403` — не с адреса из allowlist; `404` — `external_id` не известен;
`413` — тело больше 25 МБ; `422` — не прошла валидация.

## 3. Наши ответы вам (на ваш эндпоинт)

Вы даёте нам один URL и один токен (оба — заранее, отдельно для теста и
боя). Мы шлём туда `POST` с телом, где поле `"type"` говорит, что это за
событие. Отвечайте:

- `200`/`204` (любой код 2xx) — если приняли;
- **`409` с телом `{"current_status": "...", "reason": "..."}` — обязательно
  (T21), если у вас статус этой заявки уже отличается от того, что мы
  прислали в `prev_status`** (оператор сам вручную сменил статус, пока мы
  считали). Ваш эндпоинт **обязан** в этом случае не применять наш статус и
  ответить именно `409`, а в теле — **ваш текущий статус** в поле
  `current_status` (строка из вашего списка статусов) и, по желанию,
  `reason` (кто/почему сменил). Мы не станем перезаписывать, зафиксируем
  расхождение у себя и покажем его риск-менеджеру. Без этого ответа мы не
  узнаем о ручной смене статуса: 2xx мы считаем «принято и применено». На
  `409` без `current_status` мы тоже ничего не перезапишем и не будем
  повторять, но в расхождении у нас не будет вашего статуса — риск-менеджеру
  придётся выяснять его вручную.
  Пример ответа:

  ```json
  {"current_status": "approved", "reason": "оператор одобрил вручную"}
  ```
- любой код 5xx или не ответили за разумное время — мы расцениваем как
  временную недоступность и повторим позже с увеличивающейся паузой; ничего
  не потеряется.

### 3.1. После распознавания фото — `type: "ocr_result"`

```json
{
  "type": "ocr_result",
  "external_id": "APP-10492",
  "event_id": "b5b6a1b0-....",
  "fields": {
    "last_name": { "value": "Иванов", "confidence": 0.99 },
    "first_name": { "value": "Иван", "confidence": 0.98 },
    "passport_series": { "value": "4500", "confidence": 0.95 },
    "passport_number": { "value": "123456", "confidence": 0.97 }
  }
}
```

Присылается один раз после каждого успешного распознавания, не дожидаясь
решения стадии А.

### 3.2. После стадии А или стадии Б — `type: "decision"`

```json
{
  "type": "decision",
  "external_id": "APP-10492",
  "event_id": "9c3a7f10-....",
  "prev_status": "new",
  "status": "approved",
  "score": 742,
  "reason": "Одобрено: сумма 54000.00, срок 12 мес., тариф standard, первый взнос 6000.00."
}
```

| Поле | Комментарий |
| --- | --- |
| `prev_status` | Статус, который был у вас, когда мы получили заявку/анкету (эхо вашего `status` из п.1/п.2) — сверьте со своим текущим: если у вас уже другой статус, значит кто-то успел его сменить, и этот ответ можно не применять (мы и сами это уже обнаружили бы через ваш `409`, это на случай, если вы хотите проверить со своей стороны тоже). |
| `status` | Новый статус по нашей схеме соответствия (см. `docs/spec.md` → «Соответствие статусов», финальные значения уточняются и конфигурируются под вашу систему в `config/status_mapping.yaml` на нашей стороне). |
| `score` | Скоринговый балл, если он есть на этом этапе (на стадии А его не бывает — тогда `null`). |
| `reason` | Причина решения человеческим текстом, для показа оператору. Без служебных кодов. |

### 3.3. Произвольный комментарий — `type: "comment"`

```json
{
  "type": "comment",
  "external_id": "APP-10492",
  "event_id": "aa11bb22-....",
  "text": "Предложен альтернативный тариф с меньшим первым взносом."
}
```

Используется редко, для замечаний отдельно от смены статуса.

## Что мы не делаем

- Не запрашиваем у вас список заявок — опроса нет, инициатива полностью у
  вас (входящие вебхуки к нам).
- Не принимаем селфи.
- Не ждём синхронного ответа дольше `202` — результат всегда приходит
  отдельным POST-ом от нас, когда он готов (OCR — секунды, стадия А —
  секунды, стадия Б — зависит от ответа БКИ).

## Контрольный пример (локально, с нашей заглушкой `fake_partner`)

В dev-окружении роль вашей системы играет `fake_partner` — у нас есть
скрипт `scripts/e2e_check.py`, который прогоняет оба направления через неё
и проверяет 5 сценариев целиком (хороший клиент, отказ по санкциям, БКИ не
подключено, перегруз по кредитам, повтор клиента). Если нужен образец
реального трафика для своей реализации — можем прислать запись этого
прогона.
