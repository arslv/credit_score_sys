# T22 — мелкие правки после T21

## 1. ПДН 83% давал «Серую зону» — расхождение с ТЗ, исправлено

**Что было.** `limits.pti_max` (60%, в Скоринге — «ПДН: отказ выше»)
применялся только к **заявленному** ПДН до БКИ. Для ПДН **по КИ** действовало
одно правило — `soft_rules.pti_high`: выше 55% → ручная проверка; порога
отказа не было вовсе. ТЗ («Начальные значения»): «ПДН, отказ — выше 60%;
ручная проверка — 45–60%». Отсюда 83% → серая зона.

**Ваше решение:** один порог отказа `pti_max` на оба ПДН.

- `evaluate_financial`: ПДН по КИ > `limits.pti_max` → отказ `PTI_TOO_HIGH`
  раньше мягких правил; записывается как сработавшее правило с фактом и
  порогом («Долговая нагрузка по кредитной истории 83% выше порога отказа 60%»).
- Включается ключом правил `limits.pti_max_applies_to_credit_history`
  (по умолчанию `false` — старые версии правил решают как решали; в
  `dev.yaml` — `true`). Так смена логики видна в истории версий и в
  «проверить на истории».
- Пороги не менялись: 60% и 55% — те же.

**Сейчас для ПДН по КИ:** выше 60% — отказ; выше 55% (до 60% включительно) —
ручная проверка. Для заявленного ПДН до БКИ: выше 60% — отказ.

**Версия правил v44** — опубликована через симуляцию: из 100 заявок с
известным исходом (778 в выборке) **меняется 16 решений**, все — серая зона →
отказ; одобрения не меняются (доля одобрений 49% → 49%). В истории версий:
«Отказ по ПДН из КИ выше порога: выключен → включён».

**Подписи:** Скоринг — «ПДН (заявленный до БКИ и по КИ): отказ выше», «ПДН по
КИ: ручная проверка выше»; карточка — «порог отказа 60%» / «порог ручной
проверки 55%».

Тесты: `test_engine_rules.py` (83% → отказ, ровно 60% — не отказ, 58% —
ручная проверка, порог из конфига, выключено в старых версиях),
`test_engine_stage_b.py` (сквозной: /review → БКИ → 83% → `rejected_b`, текст
причины, решение заказчику — `rejected`), Playwright — подсказка и детали для
отказа по ПДН.

## 5. Playwright не меняет активную версию правил

Вернуть «ту же» версию после теста нельзя: версии append-only, откат создаёт
копию с новым номером, удалять нельзя (правило 1). Поэтому — отдельная база:

- `docker-compose.yml`, профиль `e2e`: `api_e2e` (база `dialog_e2e` на том же
  Postgres, создаётся `python -m app.cli.ensure_database` — только CREATE,
  никогда DROP) и `frontend_e2e` (порт 5174). `global-setup.ts` поднимает их
  сам (`--build`, чтобы не гонять старый код) и сеет обе базы одними учётками.
- Тест «опубликовал → откатил» вынесен в
  `ruleset-publish-rollback.isolated.spec.ts` — проект `isolated-db`.
  Остальные тесты — на dev-данных, как раньше.
- `global-teardown.ts` сверяет активную версию dev-базы до и после прогона и
  валит прогон при расхождении. Последний прогон: «активная версия правил в
  dev-базе не изменилась: 44».
