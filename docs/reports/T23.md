# T23 — демо-данные и доработка дизайна

## Часть 1. Демо-данные

```bash
docker compose stop worker beat
docker compose exec api python -m app.cli.seed_demo --password '<пароль демо-аккаунтов>'
docker compose start worker beat
```

### Решения по ходу (ваши ответы)

- **Даты за 60 дней — «виртуальные часы»** (`app/demo/clock.py`). Конвейер
  берёт время из `datetime.now()`, а `created_at` проставляет Postgres. Сид
  выполняет каждое событие под `time_machine.travel(момент)`, а слушатель
  `before_flush` ставит виртуальное время в колонки с `server_default now()`
  у **новых** строк. Ни одного UPDATE по append-only таблицам (правило 1).
  Зависимость `time-machine` — только в dev-extras.
- **`--reset` нет.** Сид работает только на пустой базе (нет заявок и
  демо-сотрудников). Иначе отказывается: «Сбросьте базу: docker compose
  down -v, затем alembic upgrade head, затем seed_demo». В
  `APP_ENV=production` тоже отказывается.

### Как устроено — через настоящий конвейер

Все шаги идут в хронологическом порядке, каждый в свой момент виртуального
времени (`app/demo/runner.py`):

1. **Вебхук заявки.** Тело собирает fake_partner: новый
   `/_test/compose-new-application`, синтетические фото паспорта с теми же
   полями, что «распознает» OCR. Доставка — в наш FastAPI-app в этом же
   процессе (ASGI).
2. **Стадия А:** `run_stage_a` с `FakeOcrProvider`. ФНС ставится в очередь
   (`.delay` перехвачен) и выполняется через ~50 с виртуального времени.
3. **ФССП** — через API оператора: поиск, капча, код. Источник фейковый, с
   заданными производствами.
4. **«Рассмотреть»:** тело собирает `/_test/compose-review`, дальше
   `run_stage_b` с `FakeBkiProvider` (отчёт из плана) или «БКИ не подключено».
5. **Решения** уходят на настоящий `/partner/webhook` fake_partner. Сценарий
   «оператор изменил статус» — режим `conflict` fake_partner (409) →
   `manual_overrides`.
6. **Комплаенс, версии правил (симуляция → публикация), сотрудники,
   справочники** — через API админки под демо-сотрудниками нужных ролей,
   поэтому аудит пишется как обычно. Реестры МВД и Росфинмониторинга грузятся
   штатными `sync_*` (атомарная замена + `registry_sync_log`).
7. **Портфель:** CSV в форматах `config/import_mappings`, штатный импорт T15
   (`/api/imports/*`), затем пересчёт `delinquency_daily`.

Worker и beat на время сида должны быть остановлены: иначе их расписание
подхватит заявки с реальным временем. Сид проверяет это через
`celery ping` и отказывается с подсказкой.

### Допущения

- **Просрочка 30–60 и 90+ за 60 дней не успевает набежать:** первый платёж
  наступает через месяц после выдачи. Поэтому 12 договоров — по
  **историческим** заявкам 4–10 месяцев назад (штатный импорт исторических
  заявок T15). Именно они дают 30–60, 90+, «погашен» и «товар изъят».
- **Категории «Автозапчасти» и «Телефоны и смартфоны»** сид заводит через
  API справочников — в исходном справочнике их не было.
- **ФИО** — случайные сочетания частых дагестанских и русских имён. Телефоны
  — `+7 999 000-xx-xx`, улицы вымышленные («ул. Демонстрационная»). Для
  совпадений с перечнем — отдельные редкие ФИО, которых нет у других
  заявителей: поиск по перечню нечёткий.
- **Версия v1** создаётся из файла при старте api в реальное время, а не
  датой пилота. Сид вызывает ту же синхронизацию в начале: на свежей базе v1
  получит дату «за 2 дня до пилота».

## Часть 2. Дизайн

**Токены** (`index.css`, `:root`): `--font-md` 14px — базовый, `--font-sm`
13px — вторичный, заголовок страницы 20px, `--row-height` 36px,
`--content-max` 1200px, `--section-gap` 24px, `--sidebar-width`,
`--settings-nav-width`, `--radius-lg`, `--color-overlay`/`--shadow-modal` —
для светлой и тёмной темы.

**Общие блоки** (`components/ui.tsx`): `PageHeader` (заголовок + одна строка
«что здесь делается» + действия), `LoadingState`, `ErrorState` (с
«Повторить»), `EmptyState` (одна фраза и не больше одной кнопки),
`SearchInput`, `Segmented`, `Modal` (Esc и клик по фону закрывают, фокус — на
первое поле), `Pagination`. Ими пользуются все экраны.

**Каркас:** пользователь и «Выйти» — внизу меню, пустой верхней полосы больше
нет. Вкладки сверху остались только у Портфеля.

**Настройки:** подменю слева — Сотрудники, Справочники, Импорт (перенесён из
Портфеля), Комплаенс, Аудит, Состояние системы; каждая роль видит только своё.
- Сотрудники — поиск, фильтр по роли, создание и правка (роль, пароль,
  отключение доступа) в модальном окне; роли подписями, а не кодами.
- Справочники — три вкладки (категории, чёрный список, причины), поиск и
  фильтр, добавление и правка в модальном окне. В чёрный список теперь можно
  внести паспорт, телефон и дату рождения — раньше форма позволяла только
  ФИО, и такая запись никогда не срабатывала: совпадение ищется по паспорту
  или телефону.
- Импорт — четыре загрузки сеткой 2×2 с пояснениями, кандидаты на привязку,
  пустое состояние.
- Комплаенс — поиск, фильтр «Все / Заморожено», замороженные сверху; причина
  и вердикт подписями.
- Аудит — фильтры по сотруднику и действию (оба есть в API), колонка «Кто»,
  подписи действий.
- Состояние системы — шапка и общие состояния; строка-итог и «Подробности»
  без изменений.

**Справка:** липкое оглавление слева с подсветкой текущего раздела, схема
пути заявки (блоки со стрелками, исходы под стадиями, шаг человека —
пунктиром), короткие разделы, поиск по терминам с подсветкой.

**Остальные экраны:**
- Заявки — одна строка на заявку: «№ у заказчика», «Товар» с обрезкой; до
  «Рассмотреть» — прочерк вместо «0 ₽ / 0 мес.»; у наблюдателя и
  администратора нет всегда пустых «Нужно сделать» и «Ждёт».
- Договоры — фильтр по состоянию.
- Договор — «Условия» и «Состояние» двумя колонками, график и платежи рядом.
- Скоринг — поля сеткой, блок публикации «проверить → описать →
  опубликовать», колонка симуляции липкая.
- Аналитика, клиент, карточка заявки, вход — единые шапки и состояния.
- Тариф «Выгодный» в карточке выводился прочерком — подписи добавлены для
  всех тарифов.

Логика не менялась: ни одной строки в `backend/app/engine`, `api`, `sources`.
Бэкенд в части 2 не трогался.

## Аналитика — переделана

Данные и запрос те же, другая подача:

- **Период**: быстрые 30 дней / 90 дней / полгода или свои даты.
- **Ряд из 5 ключевых цифр**: заявок за период, одобрено (доля от поданных),
  доля одобрений стадии Б, отказов (главная причина), договоров с
  просрочкой (и сколько 90+).
- **Три блока**: «Заявки и решения» → «Портфель» → «Операционное». У каждого
  графика по-прежнему заголовок-вывод.
- **Графики** — HTML/CSS без библиотек, подсказка при наведении:
  - воронка с конверсией от предыдущего шага;
  - одобрения по неделям столбиками со средней линией; бледные столбики —
    недели меньше чем с 5 решениями; лучшая и худшая — только среди
    завершённых недель;
  - причины отказов — полосы с долей;
  - балл БКИ — гистограмма с зонами по порогам и легендой;
  - просрочка — одна полоса по корзинам с легендой и числами;
  - по месяцу выдачи — таблица с мини-шкалой доли плохих.
- **Цвета** проверены `validate_palette.js`, светлая и тёмная тема:
  - корзины просрочки (`--dq-*`) — один тон, монотонная светлота;
    «без просрочки» — нейтральный серый вне шкалы;
  - зоны балла (`--zone-*`) — различимы, в том числе при нарушениях
    цветового зрения.

## Открытые вопросы

1. **Очередь «Требуют действия» у риск-менеджера содержит ВСЕ заявки** (162
   вместо 39). `_latest_override_mismatch_clause`
   (`app/api/applications.py`): подзапрос внутри `exists()` не связан с
   внешней строкой заявки, и одно расхождение с оператором где угодно
   включает в очередь всё подряд. Проявилось только на демо-данных. Это
   логика, в T23 её трогать нельзя — вынесено отдельной задачей.
2. **Поручитель при повторном «Рассмотреть».** Каждый прогон стадии Б
   заводит новую строку `guarantors`, а `_fssp_checked_for_decision` берёт
   поручителя заявки без сортировки (`.first()`). Проверка ФССП «старого»
   поручителя засчитывается или нет в зависимости от порядка строк. В демо
   три такие заявки одобрились, но поведение не гарантировано. После
   повтора строки остаются в статусе `checking`.
3. **Vite в Docker на Windows** не видит изменений файлов (bind mount без
   inotify) — после правок фронтенда нужен `docker compose restart frontend`.
   Можно включить `server.watch.usePolling` — отдельное решение.

## Рейтинг клиента (документ заказчика «Рейтинг клиента.docx»)

Экспертная скоркарта заказчика: баллы по критериям **складываются** в одну
сумму. Реализовано то, что в документе однозначно:

- **Возраст** — шкала из документа (до 21: −500, с поручителем 0; 40–55: +100;
  66+ — только с поручителем).
- **Контакты** — кто дал номера: родители и брат/сестра +100; до 30 лет без
  родителей −150; только друзья −150.
- **Работа** — по словам в месте работы/должности: госработа +300, Газпром/
  Сбер/РЖД +230, … курьер/охранник 0.
- **Прописка** — районы Дагестана по группам (+100 … −200), отказные сёла.
- **Автозапрос поручителя** — до 21 года, от 66 лет, прописка «только с
  поручителем», отказное село, телефон от 50 000 ₽ при возрасте до 24 лет.

Где: раздел `client_rating` в `config/rulesets/dev.yaml` (все баллы и списки —
конфиг), расчёт — `app/engine/client_rating.py`, в карточке заявки — блок
«Рейтинг клиента» (сумма, разбивка, нужен ли поручитель). Значения критериев
(возраст, место работы, район) видят только роли с доступом к персданным,
баллы — все.

**Пока информационно — на решение не влияет**: порогов суммы нет. Нет данных
по критерию — пункт «нет данных», в сумму не входит, карточка пишет, что
сумма неполная.

Анкета «Рассмотреть» принимает новые необязательные поля:
`employment.employer`, `employment.position`, `contacts[]`
(`docs/integration_contract.md`). В текущих демо-заявках их нет — у них
посчитаны только возраст и прописка; новый сид их заполняет.

## Карточка заявки — стадии А и Б раздельно, рейтинг наверху

- **Рейтинг клиента** — цветная карточка сразу под вердиктом: сумма крупно,
  плашки по критериям (зелёная — плюс, красная — минус, серая — нет данных),
  нужен ли поручитель; таблица с правилами — по кнопке «Разбивка по критериям».
- Рядом — **ключевые факты**: ПДН против порога, ФССП, поручитель, сумма и срок.
- **Путь заявки** — шкала «Подача → Стадия А → Звонок оператора → Стадия Б»
  с цветом исхода и датами, под ней **две карточки стадий**: исход, причины
  (у стадии последнего решения), проверки именно этой стадии с отметками
  ✓/✕/! и кнопкой «Повторить» у упавших. Стадия, до которой дело не дошло, —
  бледная, с пояснением.

## Три роли и «Проверка по перечням» (решение владельца)

**Ролей три вместо пяти.** `admin`, `operator`, `viewer`. Обязанности

`admin`; совпадения с перечнем разбирает и `operator`.

| Роль | Что может |
|---|---|
| Администратор | всё: Скоринг, Аналитика, Проверка по перечням, ФССП, повтор проверок, Сотрудники, Справочники, Импорт, Аудит, Состояние системы. Очередь — серая зона, расхождения с оператором, заморозки по перечню |

| Наблюдатель | смотрит Заявки, Аналитику, Портфель, Справку; ничего не меняет, очереди нет |
