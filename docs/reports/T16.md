## Часть 1 — ФНС (service.nalog.ru / egrul.nalog.ru / statusnpd.nalog.ru)

**Разведка (живая, до написания кода):** все три формы отвечают без ключа и без договора. `fns_inn` (ФИО+паспорт→ИНН) и `fns_egrip` (ИП по ИНН) — одна платформа (общий стек статики «uni»), двухшаговый протокол: сначала проверяем, не нужно ли отдать согласие на обработку ПД (`_ensure_consent`, относительный URL, не от корня — это и было живой находкой: форма согласия лежит в `/static/...` относительно страницы согласия, не сайта), затем POST с `c=find`, затем поллинг `c=get` с растущей задержкой. `fns_npd` (самозанятость) — прямой POST, без согласия, без капчи на разведке.

**Капча у ФНС:** увидела её один раз на разведке — это оказался статический файл-пример (`/static/captcha-dialog.html`), не подтверждённый отклик именно на мою частоту запросов. **Честно: порог не измерен.** Выбран консервативный интервал — **20 секунд** между запросами на общий троттл-ключ `fns_inn`/`fns_egrip` (`fns_shared_request_interval_seconds`), **30 секунд** для `fns_npd` (документированный лимит ФНС — не больше 2 запросов в минуту с одного IP, 30 с — это ровно предел с небольшим запасом на джиттер). При `captchaRequired=true` от сайта — код **не решает капчу** (ваше жёсткое правило), откатывается на `fns_retry_backoff_seconds` (20 с) и повторяет до `fns_max_attempts` (5), после — `source_unavailable`.

**Архитектура (главное изменение против исходного плана):** ФНС больше не блокирует ни одну стадию. `run_stage_a` вызывает `queue_fns_checks()` (ставит `fns.run_checks` в Celery) и **сразу** финализирует стадию А — без ожидания. Результат приходит в карточку заявки асинхронно, когда отработает фоновый воркер. Стадия Б: если результат ФНС ещё не пришёл — признак `features.fns_*` просто отсутствует («не вычислимо» для движка правил, ничего не блокирует, т.к. ни одно правило в `dev.yaml` на ФНС не завязано как hard_stop).

**Тесты:** `tests/test_sources_fns.py` (28 тестов, фейки + respx против полного протокола, включая капчу→backoff→`source_unavailable` после исчерпания попыток), `test_fns_checks_queued_after_stage_a_finalizes_without_waiting` (стадия А не ждёт).

## Часть 2 — ФССП (is-go.fssp.gov.ru), капча решает только человек

**Разведка (живая):** старый протокол `api-ip.fssp.gov.ru` закрыт с 2022 — опрашивать нечего, таблица `fssp_requests` (T09) удалена. Новый протокол сайта — два GET на `/ajax_search`, JSONP-ответ с HTML внутри: `search()` возвращает картинку капчи (base64 PNG в `data:image/png;base64,...`) и `code_id`; `submit_code()` с тем же `code_id` и введённым кодом возвращает либо результат, либо отказ. Куки не нужны — подтверждено дважды живым тестом. Неверный код не даёт мягкое «попробуйте снова»: конкретный `code_id` сгорает немедленно, но **свежий** `code_id` (новый `search()`) тут же принимает верный код — тоже подтверждено живым тестом, отдельной сверочной проверкой перед планом.

**Регион:** серия паспорта — код места **выдачи**, не прописки, поэтому для выбора региона ФССП не используется вообще (ваше явное указание). `config/fssp_regions.yaml` — 88 кодов, снято целиком с выпадающего списка сайта. Подсказка (`app/engine/fssp_regions.py::match_region_code`) сравнивает значимые слова адреса регистрации с названием региона (все слова названия должны встретиться в адресе — защита от ложных совпадений вроде «Карачаево-Черкесия» по одному только «Черкесску»), но **никогда не подставляется молча**: оператор выбирает сам из полного списка, подсказка — только предзаполнение, которое видно и можно поменять.

**Протокол в приложении (`app/api/fssp.py`):**
- `POST /applications/{id}/fssp/search` — резолвит `Subject` (заявитель через последний OCR, поручитель через `Guarantor.profile`), требует явный `region_code` из списка, при повторной проверке того же субъекта требует `reason` (иначе 409). Любая ещё не закрытая сессия (`status=pending_captcha`) по этому же `(application, subject)` гасится (`status=expired`) — её `code_id` после этого не принимается.
- `POST /applications/{id}/fssp/{session_id}/submit-code` — неверный код → сессия сгорает, **автоматически** открывается новая капча с сообщением «Код неверный, введите новый» (ваше решение по UX); сайт недоступен → `source_unavailable`, без автоповтора; код принят → `checks(source=fssp)` с классификацией (`app.engine.fssp.summarize_productions`), и если по заявке уже есть решение, а результат сработал бы на `hard_stop fssp_credit_debt` — `fssp_post_decision_alerts` (статус заявки не трогаем, правило 12 CLAUDE.md).
- Картинка капчи и введённый код не попадают ни в логи, ни в аудит — в `audit_log` только факт (кто, когда, субъект, регион, результат). Ответы с капчей — `Cache-Control: no-store`.
- Роли — только `operator` и `risk_manager` (ваш п.1: `admin` персданные заявителей не видит по нашей модели, убран).

**Парсер результата (оговорка, важно):** оба живых теста на разведке вернули «ничего не найдено» — реального HTML с найденным производством в руках не было. `parse_fssp_result_html` написан по вашему словесному описанию структуры (поля `data-name="predmet"/"summa"` в document order), помечен в докстринге как непроверенный на реальном «найдено»: при первом реальном совпадении в проде нужно сверить и, возможно, поправить. Если разбор не удаётся — `status=error` с сырым HTML, оператор видит сам, автоотказа отсюда не бывает ни при каком исходе.

**`fssp_required_for_approval` (ваш п.2):** новый ключ `RulesetConfig` (по умолчанию `true`). Без пройденной проверки ФССП (заявитель и поручитель, если используется) `approve` недостижим — максимум `gray_zone` с `reason_code=FSSP_NOT_CHECKED`, тем же путём, что `BKI_NOT_CONFIGURED`.

**ФССП после решения (ваш п.3):** `fssp_post_decision_alerts` — append-only факт-лог (в отличие от `fssp_captcha_sessions`, которая техническое состояние и обновляется на месте). Счётчик — `GET /api/system/status` → `fssp_results_after_decision`. В карточке заявки — предупреждение (`FsspPanel.tsx`): «ФССП найдено после того, как решение по заявке уже было принято — пересмотрите вручную».

**Одна активная сессия (ваш п.5):** проверено тестом на двух «одновременных операторов» (`test_fssp_two_operators_concurrent_search_invalidates_older_session`) — второй `search()` гасит сессию первого, его `code_id` отклоняется с 409.

**Тесты:** `tests/test_sources_fssp.py` (28), `tests/test_api_fssp.py` (7: роли, happy path, неверный код → автоповтор, два оператора, обязательная причина при повторе, предупреждение после решения).

## Живой прогон

Два заезда, `EXTERNAL_SOURCES_MODE=http` (реальные ФНС/ФССП), ваши реальные данные (ФИО, дата рождения, паспорт, адрес регистрации — собраны через чат, не сохранялись за пределами `tmp/live_checks/`, в этот отчёт не попадают).

**Заезд 1 — ФНС прошла, ФССП — нет.** `fns_inn`/`fns_npd`/`fns_egrip` отработали в фоне на реальных сайтах nalog.ru и вернулись успешно (`fns_inn: ok`, ИНН найден; `fns_npd: ok`; `fns_egrip: no_data`) — сырые ответы сохранены (`tmp/live_checks/fns_live_20261006.json`). ФССП — ошибка «не нашли капчу в ответе сайта». Прямой повторный вызов `source.search()` с тем же Subject из скрипта отработал нормально — значит, не сайт. Проверила `audit_log`/`fssp_captcha_sessions` по вашей попытке — пусто вообще, значит `search()` падал до записи чего-либо. Проверила реальный HTTP-запрос по логам `uvicorn` — `is[last_name]=&is[first_name]=&is[patronymic]=&is[date]=` — **все поля пустые**.

**Найденный баг:** `OcrResult.fields` в БД — обёртка `{"fields": {...}, "flags": {...}, "below_threshold": ...}` (`app/ocr/service.py::run_ocr`), а не сами поля распознавания. `app/api/fssp.py::_resolve_subject` и `retry_check` в `app/api/applications.py` передавали эту обёртку целиком в `_subject_from_ocr`, которая ждёт плоский словарь — получали пустой `Subject` (ФИО/дата рождения — `None`). Настоящий путь стадии А (`finalize_stage_a`) этой ошибки не имел — там распаковка уже была (`app/engine/pipeline.py:486`, единственное корректное место до этой правки) — поэтому ФНС (идёт через стадию А) сработала, а ФССП и повтор ФНС через ручную кнопку (оба — через два буквально проверенных эндпоинта) — нет.

**Починено в корне, не точечно (по вашему указанию):**
1. Один хелпер `app.engine.pipeline.unwrap_ocr_fields()` — grep нашёл все места чтения `OcrResult.fields` (список — в коммите/диффе): два бага (пофиксены через хелпер), одно уже корректное место (переведено на тот же хелпер для единообразия), один умышленный полный passthrough в API-ответ для фронта (не трогала, задокументировала), один JSONB-путь прямо в SQL-запросе (не читается в Python, хелпер неприменим — задокументировано).
2. `missing_subject_field_error()` (`app/sources/base.py`) — общая проверка для `fns_inn`/`fssp` (и `Fake*`, и `Http*`-реализаций): пустое обязательное поле (ФИО/дата рождения, для `fns_inn` — ещё паспорт и дата выдачи) → понятная ошибка `«Нет данных для проверки: не заполнено ...»`, без единого обращения к сайту.
3. Фейки (`FakeFnsInnSource`, `FakeFsspCaptchaSource`) теперь падают на пустом `Subject` той же проверкой — этот класс багов поймают тесты и дальше. В `test_api_applications.py` для `fns_inn`-ретрая фейку засеян ответ «найден» под корректный субъект, проверяется `status == "ok"` и сам переданный `Subject` (через `check_calls`), не только статус «не unavailable».

Неудачная попытка ФССП теперь оставляет след: `audit_log` всегда (кто, когда, тип ошибки — без картинки и кода, как и раньше), `checks(source=fssp, status=source_unavailable)` с сырым ответом сайта — когда сайт реально отвечал (`FsspSearchError.raw_response`); на отказ валидации (сайт не запрашивался) `checks`-строка не пишется — там нечего сохранять, только `audit_log`.
5. Сообщение «сайт ответил без капчи» — только когда сайт реально ответил без неё; сетевая ошибка/таймаут — «сайт недоступен: ...»; пустой субъект — отдельное `422 Нет данных для проверки: ...`, без похода на сайт вовсе.
