# T21 — две правки перед запуском

## 1. ПДН включает платёж по новой рассрочке

**Было:** ПДН = платежи по действующим кредитам из КИ / доход — нагрузка
недооценена ровно на платёж по нашей же рассрочке.

**Стало** (ваше решение по источнику платежа):

- ПДН = (платежи по действующим кредитам из КИ + ежемесячный платёж по нашей
  рассрочке) / доход.
- Заявленный ПДН (фильтр до БКИ) = (заявленные клиентом платежи + тот же
  платёж) / доход — как и раньше, только до БКИ.
- **Откуда платёж:** основной источник — `deal.monthly_payment` из `/review`
  (их график с наценкой, точная цифра; поле добавлено в
  `integration_contract.md` и `openapi.yaml` как обязательное для расчёта
  ПДН). Нет поля — запасной расчёт по тарифу: (цена − взнос) ×
  (1 + `tariffs.<тариф>.markup_pct`) / срок, в карточке пометка «платёж
  рассчитан по тарифу, не из системы заказчика». Нет ни поля, ни наценки
  тарифа — ПДН «не вычислимо (нет платежа по рассрочке…)», а не заниженная
  цифра.
- **Наценки тарифов — `markup_pct: 0.0` у всех трёх. Реальные значения
  нужно получить у заказчика** (в ТЗ это открытый вопрос «размер наценки по
  каждому тарифу»). До этого запасной расчёт = (цена − взнос) / срок.

Код: `app/engine/bki_features.py` (`compute_installment_payment`, новые
аргументы `compute_declared_pti_features`/`compute_bki_features`, причина
`pti_unavailable_reason` в снимке), `app/engine/stage_b_pipeline.py`
(`STAGE_B_FEATURE_SET_VERSION = "stage_b.v2"`), `app/engine/schema.py`
(`TariffConfig.markup_pct`), `app/api/partner_webhooks.py`
(`ReviewDealIn.monthly_payment`, сырое значение — в снимке анкеты, правило
3), `app/api/applications.py` (`installment_payment`,
`installment_payment_source`, `pti_status="no_installment"`).

**Карточка:** «ПДН 48% (с учётом платежа по рассрочке 6 500 ₽) — порог
60%». Если ПДН сам — причина решения, сумма платежа показывается деталью
в «Причине» (в строке вердикта её нет). Попутно исправлено: подсказка «?»
у серой зоны по ПДН называла порог отказа (60%), а сработало правило ручной
проверки (55%) — теперь берётся порог сработавшего правила.

### Новая версия правил и «проверить на истории»

Версия опубликована обычным путём — симуляция → сохранение с комментарием
(через API, тот же поток, что экран «Скоринг»), историю не правил:
**v39** («T21: ПДН включает платёж по нашей рассрочке; наценки … пока 0»).
v38 — та же версия, но с датой вступления из файла (2026-01-01): она
проиграла по дате активной v37 (созданной откатом в Playwright сегодня) и не
стала активной; v39 — повтор с датой «сегодня». Обе — append-only, ничего не
удалялось. После прогона Playwright активна v43 — копия при откате в его
тесте, содержимое совпадает с файлом (наценки на месте).

Симуляция теперь видит смену формулы: снимки стадии Б до T21 (ПДН без
рассрочки) для версии правил С наценками досчитываются тем же платежом
(`add_installment_to_legacy_stage_b_features`, по сделке и доходу из снимка
анкеты). Без этого «проверить на истории» показал бы 0 изменений по
определению.

**Результат на dev-базе (вся история, 759 заявок):**

| | |
| --- | --- |
| Заявок с известным исходом по обеим версиям | 93 |
| **Решений изменится** | **0** |
| Доля одобрений | 49,5% → 49,5% |
| Решений стадии Б с ПДН | 68 |
| Рост ПДН | в среднем +4,0 п.п., максимум +5,0 п.п. |
| ПДН > 55% (ручная проверка) / > 60% (отказ) | 15 → 15 / 15 → 15 |

Почему ноль: в dev почти все заявки синтетические — доход 90 000 ₽,
сделка 54 000 ₽ на 12 мес., платёж 4 500 ₽ = +5 п.п.; ни одна заявка не
была в полосе 50–55%. На реальном портфеле (крупнее сделки, короче сроки,
реальная наценка) сдвиг будет больше — прогоните «проверить на истории» на
бою после получения наценок.

  `current_status` — всё в `integration_contract.md`.

  больше нет); в общий прогон не входят, не чинил — вне рамок задачи.

  предложит альтернативный тариф (лимиты), ПДН не пересчитывается под него.
