# T17 — редизайн админки: отчёт

Задача — только интерфейс: разложить 11 плоских вкладок в разделы по смыслу,
убрать сырые коды с экрана, объяснять решения человеческим языком, починить
честность цифр (пороги — из версии решения, не из текущего конфига; балл БКИ
как есть, без выдуманной собственной скоринговой карты). Бизнес-логика и
данные не менялись нигде, кроме отображения.

## Порядок работы

1. Аудит скриншотами текущего интерфейса (`docs/design/before/`).
2. Статические макеты (`docs/design/mockups/`) — приняты вами перед реализацией.
3. Реализация по частям, с вашими правками после каждой: навигация и роли →
   карточка заявки → Скоринг → список заявок → Аналитика → справка.

Каждая часть: pytest, Playwright, `scripts/e2e_check.py` зелёные, скриншоты в
`docs/design/after/<часть>/` — перед тем, как считать часть готовой.

## Часть 1 — навигация и роли

5 разделов вместо плоского списка: Заявки, Скоринг, Аналитика, Портфель,
Настройки. Раздел с несколькими экранами получает вторичную строку вкладок.
Видимость — по роли, пустых разделов в меню нет. Иконки — один набор
(lucide-react), единый размер и толщина линии, без эмодзи.

## Часть 2 — карточка заявки

- **Баг с Росфинмониторингом.** Карточка писала «стоп-факторов нет» при
  отказе: показывались только `triggered_rules`, а повторная заморозка по
  перечню пишет их пустыми по дизайну (`_reject_for_active_freeze`). Плюс сид
  был неполным — без проверок, истории, снимка признаков. Исправлено в двух
  местах: бэкенд отдаёт `reason_text` (тот же текст, что в комментарии
  оператору, с фолбэком на `reason_code`, когда сработавших правил нет), сид
  переписан по форме того, что реально пишет конвейер.
- Подписи решений зависят от этапа: `decisionOutcomeLabel(stage, outcome)` —
  на стадии А `manual_review` это «Передано оператору», на стадии Б —
  «Серая зона». Этапы — «А»/«Б» кириллицей.
- Статусы проверок — через словарь по источнику (`checkResultLabel`), без
  сырых `ok`/`hit`/`no_data` на экране.
- Блоки «Клиент» и «Сделка» по макету (человеческие значения: пол, занятость,
  категория товара из справочника). Сырьё (распознавание, снимки анкеты) — в
  свёрнутых «Подробностях»; одинаковые подряд идущие снимки не дублируются.
- «Почему такое решение» для одобрения/серой зоны — сравнения «Балл БКИ Х —
  порог Y» и «ПДН X% — порог Y%», пороги — из версии правил ИМЕННО ЭТОГО
  решения (`decision.ruleset_version_id`), не из текущего активного конфига.
- Форматы: баллы без копеек, суммы с пробелами и ₽, даты ДД.ММ.ГГГГ, время
  с «МСК».

## Часть 3 — Скоринг

- Публикация версии правил требует непустой комментарий; история версий
  показывает, что изменилось («Порог отказа (балл БКИ): 450 → 460»).
- Форма с типовыми полями (пороги, лимиты, ПДН) поверх YAML — валидатор
  принимает числа, пришедшие из YAML строкой.
- «Экспертный режим» (сырой YAML) — в свёрнутом блоке.

## Часть 4 — список заявок

- **Очередь «Требуют действия» — у каждой роли своя**, не общий список:
  оператор (позвонить / проверить ФССП), комплаенс (совпадения по перечню,
  ждут снятия), риск-менеджер (серая зона, оператор изменил статус).
  Наблюдатель и администратор очереди не имеют — чипа у них нет. Счётчики —
  с сервера (`GET /api/applications/quick-counts`), та же цифра, что в списке.
- Сортировка очереди — по времени ожидания (дольше всех — сверху); колонка
  «Ждёт» показывает его только у заявок самой очереди.
- Колонки, которые у роли всегда пусты, не показываются (у комплаенса —
  «Балл БКИ» и «Итог оператора»).
- Цвета статусов и точек действия — токенами в `index.css`, светлая и тёмная
  тема: янтарный только у серой зоны, «в процессе» — нейтральный серо-синий.
- **Производительность.** Очередь сначала считалась в Python (каждая заявка —
  отдельная сборка строки, 8–9 запросов): на ~260 заявках оператора ответ
  занимал 1.35 с. Сортировка и страница перенесены в SQL — 0.20 с. Такой же
  N+1 нашёлся в «Ручные переопределения и расхождения» на Аналитике (часть 5)
  и исправлен тем же способом.
- ФИО в списке теперь видит оператор — ваше явное решение; правило
  скорректировано в CLAUDE.md и `docs/spec.md` («роль operator»/раздел про
  оператора).

## Часть 5 — Аналитика

- Воронка — конкретная последовательность из ТЗ: «Поступило → Передано
  оператору → Рассмотрено (стадия Б) → Одобрено» (без «прошли стадию А» —
  на стадии А одобрения не бывает). Одним SQL-запросом с `EXISTS`+`FILTER`,
  не циклом по заявкам.
- Блок «Ручные переопределения и расхождения» переписан с Python-цикла
  (2 запроса на заявку) на `DISTINCT ON` + join — тот же паттерн, что в
  очереди списка.
- Новый блок — распределение балла БКИ по решениям стадии Б, с порогами
  действующей версии правил (без учёта матрицы по сумме — общий ориентир по
  порфелю, не порог конкретного решения; в карточке порог решения остаётся
  из его собственной версии).
- У каждого графика — заголовок-вывод, а не нейтральное название блока
  («До одобрения доходит 2% поданных заявок», «Чаще всего недоступен
  источник «ФНС — ИНН» (1%)» и т.п.) — вывод считается на фронте из уже
  пришедших чисел, порогов в коде фронта нет.
- Пустые состояния объясняют, откуда возьмутся данные («Появится после
  импорта платежей («Портфель» → «Импорт»)», «Появится после первых
  выданных договоров» и т.п.), а не просто «данных нет».
- МВД исключён из «Недоступности источников» в самом SQL-запросе, не на
  фронте постфактум.
- Замер на текущей базе (~450 заявок): `/api/dashboard/summary` — 0.11 с,
  с периодом — 0.05 с.

## Часть 6 — справка и подсказки

Новый раздел «Справка» (`/help`), виден всем ролям: путь заявки по стадиям,
три рычага, которые влияют на решение (правила / ручное решение оператора /
комплаенс), таблица ролей (с подсветкой своей строки) и термины. Подсказки
`Term` на «скор (балл БКИ)», ПДН, серую зону, стоп-фактор, стадию А/Б,
«не вычислимо», БКИ и ФССП — той же формулировкой, что на странице справки.

## Финальные пункты

### Тест «ни одно значение enum бэкенда не без подписи»

`frontend/e2e/enum-coverage.spec.ts` — читает текстом (без браузера и без
поднятого API) сам бэкенд: Python-тюплы статусов/видов из `app/models/*.py`
(те же тюплы, что задают `CHECK CONSTRAINT` в БД — `APPLICATION_STATUSES`,
`CONTRACT_STATUSES`, `DECISION_OUTCOMES`, `STATUS_HISTORY_ACTOR_TYPES`,
`DOCUMENT_KINDS`, `CHECK_SUBJECT_TYPES`, `LIQUIDITY_LEVELS`,
`REASON_CODE_KINDS`) и `config/status_mapping.yaml::reason_notes` (все
операционные причины решения) — и сверяет каждое значение со словарём
`frontend/src/lib/labels.ts`. Новое значение без подписи валит тест, а не
тихо показывается на экране сырым кодом.

Запуск этого теста сразу нашёл два места, которые пропустили более ранние
шаги: `Настройки → Справочники` показывал `liquidity` (`high`/`medium`/`low`)
и вид кода причины (`reject`/`override_approve`/`override_reject`) сырыми
значениями — добавлены `liquidityLabel`/`reasonCodeKindLabel`.

(Статусы проверок — отдельный тест `labels-dictionary.spec.ts`: там подпись
зависит ещё и от источника, не только от статуса.)

### Сверка решений сид-заявок 1:1

Движок и правила в T17 не менялись — ни одной строки в `app/engine/*`.
Проверка: взял решения четырёх представительных сид-заявок (отказ по
перечню, одобрение стадии Б, серая зона «ФССП не проверено», расхождение с
оператором) прямо из таблицы `decisions` — она append-only (правило 1
CLAUDE.md), значит это и есть то, что когда-то решил конвейер, — и сверил
с тем, что сейчас отдаёт `GET /api/applications/{id}`. Все поля (`outcome`,
`reason_code`, `freeze`, `score`, `approved_amount`, `approved_term`)
совпали дословно на всех четырёх заявках — редизайн показывает то же
решение, что было, просто понятнее.

## Что изменилось в инфраструктуре попутно

- Код в контейнеры больше не копируется (`docker compose cp`) — ни бэкенд
  (пересборка `docker compose build api worker` как обычно), ни тестовые
  скрипты: `e2e_check.py` передаёт `_e2e_runner.py` в контейнер через
  `python3 -c`, `frontend/e2e/global-setup.ts` сеет через stdin. Причина —
  скопированный файл переживал правки и один раз дал прогон на старом коде.
- `scripts/e2e_check.py` сбрасывает заглушку заказчика (`POST /_test/reset`)
  в начале прогона; заглушка на каждый запуск/сброс берёт новый случайный
  префикс `external_id` (было: один и тот же на весь процесс) — без этого
  повторный прогон против той же dev-базы собирал `external_id`, уже занятые
  прошлым прогоном, и приём (идемпотентный по `external_id`) их молча
  пропускал.

## Допущения и открытые вопросы

- Распределение балла БКИ на Аналитике использует пороги ДЕЙСТВУЮЩЕЙ версии
  правил без учёта матрицы по сумме сделки — общий ориентир по портфелю.
  Если нужен учёт матрицы, это отдельная (не однозначная для агрегата по
  многим суммам) задача.
- Виды платежа (`regular`/`penalty`/`reversal`, `PAYMENT_KINDS`) и исход
  закрытия договора (`CLOSURE_OUTCOMES`) переведены в карточке договора
  условными текстами (не функцией-словарём) — проверены вручную, в
  `enum-coverage.spec.ts` не включены; при добавлении нового вида платежа
  тест этого не поймает.
- Очередь риск-менеджера на скриншотах части 4 — 47 заявок, в основном из
  накопленных за день прогонов e2e (одноразовые тестовые имена вида
  «Плейрайт…», «Обычнов…») — это особенность dev-базы, не продакшена.

## Финальные правки перед мержем

После вашего просмотра частей 5–6 — восемь точечных правок.

**Аналитика:**

1. **Баг: заливка баров нигде не была видна** (воронка, причины отказов,
   балл БКИ, просрочка — везде только серая дорожка). Причина — `.bar-fill`
   рендерится как `<span>`, то есть `inline`-элемент, а `width`/`height` из
   стилей на инлайновых элементах браузер игнорирует. Добавлен `display:
   block` в `.bar-fill` (`index.css`) — один CSS-токен чинит все графики
   сразу, подтверждено скриншотом и Playwright-тестом на `boundingBox().width
   > 0`.
2. **Блок «оператор»: две одинаковые цифры без объяснения.** Вторая цифра
   («разошлись с системой») теперь доля ОТ переопределённых, а не от всех
   заявок, с подписью «из них» — структурно другое число, и даже когда оно
   совпадает по значению с первым (например, 100%, если все переопределения
   были расхождениями), подпись сама объясняет, почему.
3. **Заголовок-вывод по источникам — порог из конфига, не из кода.** Новая
   секция `dashboard.source_unavailable_warn_threshold` в схеме правил
   (`app/engine/schema.py`, значение — `config/rulesets/dev.yaml`, по
   умолчанию 0.05, если версия битая/отсутствует). Ниже порога —
   «Источники работают стабильно», выше — «Чаще всего недоступен источник …».
4. **Форматы.** Недели — «с ДД.ММ.ГГГГ», месяцы — «октябрь 2026 г.» (новый
   `formatMonth` в `lib/format.ts`). Поля периода: нативный календарь
   `<input type="date">` форматируется по локали ОС браузера, а не по
   атрибуту `lang` страницы и не по локали контекста Playwright — проверено
   отдельным зондом, оба способа не сработали. Рядом с каждым полем теперь
   подпись ДД.ММ.ГГГГ тем же `Intl`-форматтером, что в карточке — не зависит
   от окружения пользователя.
5. **Переименования:** «Винтажный анализ» → «Просрочка по месяцу выдачи»,
   «Когорта» → «Месяц выдачи», «ещё не зрела» → «рано оценивать».

**Справка:**

6. МВД убран из описания стадии А (в глоссарии и подсказке `Term`) — он не
   подключён и не должен упоминаться как часть пайплайна.
7. «Оператор» в таблице ролей переписан как один человек с двумя задачами
   (звонит клиенту в системе заказчика и проверяет ФССП у нас), без
   «не путать с оператором заказчика».
8. «Правила (конфиг)» → «Правила и пороги», «YAML-версии правил» → «одной
   версии правил» — без слов YAML/конфиг в тексте для людей (Rulesets.tsx
   не трогался: там это точное название реального режима «сырой YAML»,
   не нейтральная проза).

Новые тесты: `e2e/analytics.spec.ts` — ненулевая ширина заливки бара,
формат недель/месяцев/подписи дат, текст «из них разошлись с системой»,
переименования, заголовок источников. `test_api_dashboard.py` — значение
`source_unavailable_warn_threshold` из `dev.yaml`.

Финальный прогон: pytest 556 passed · Playwright 35 passed · e2e_check 5/5.
