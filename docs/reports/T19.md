# T19 — Подготовка к установке на сервере заказчика

Боевая конфигурация, бэкап/восстановление Postgres, оповещения в Telegram,
чек-лист для сисадмина.

## Состав реализации

- `docker-compose.prod.yml` (новый) — без `fake_partner`, `APP_ENV=production`
  зашит (не переопределяется из `.env`), `nginx` спереди (HTTPS, статика
  фронтенда, прокси `/api`), сервис `backup` (ежедневный дамп), фиксированная
  подсеть с адресом `nginx` (`172.28.0.10` по умолчанию) — для корректного
  `--forwarded-allow-ips` у `uvicorn` (T12: «именно адрес прокси, не маска
  подсети и не `*`»). Обязательные переменные (`POSTGRES_PASSWORD`, `DOMAIN`,
  `ANTHROPIC_API_KEY`, `PARTNER_INBOUND_TOKEN`, `PARTNER_OUTBOUND_URL`,
  `PARTNER_OUTBOUND_TOKEN`) оформлены через `${VAR:?сообщение}` — `docker
  compose up` сразу и понятно откажется стартовать без них, не тихим багом
  позже.
- `deploy/nginx/nginx.conf.template` — envsubst-шаблон (встроенный механизм
  официального образа `nginx`): редирект 80→443, `X-Forwarded-For`
  **перезаписывается** `$remote_addr` (не дописывается) — та же защита от
  подмены адреса, что и было зафиксировано в T12.
- `frontend/Dockerfile.prod` (новый) — `npm ci && npm run build`, статика
  собирается одноразовым сервисом `frontend-build` в именованный volume,
  который `nginx` потом отдаёт `read-only`. Проверено живой сборкой
  (`docker build`) — 1992 модуля, собирается за ~4 с.
- `scripts/backup_postgres.sh` — `pg_dump -Fc`, ежедневно (сервис `backup`,
  режим `loop`, интервал `BACKUP_INTERVAL_SECONDS`), ротация по
  `BACKUP_RETENTION_DAYS` (по умолчанию 14, из env), маркер
  `$BACKUP_DIR/.last_success` обновляется только при успехе — на нём
  держится алерт «бэкап не сделан».
- `scripts/restore_postgres.sh` — восстановление дампа в боевую (или любую
  названную) базу, `pg_restore --clean --if-exists`, с 5-секундной паузой на
  отмену (разрушительная операция).
- `scripts/verify_backup_restore.sh` — «проверка восстановления на тестовой
  базе» (ваше явное указание): поднимает временную `dialog_restore_check`,
  восстанавливает туда последний (или указанный) дамп, проверяет
  `applications`/`alembic_version`, удаляет временную базу. Не трогает
  боевую ни на одном шаге.
- `backend/app/alerts/telegram.py` — `send_telegram_alert`, никогда не
  бросает исключение наружу (тот же принцип, что правило 4 CLAUDE.md для
  внешних источников); пустой токен/chat_id — тихо пропускает с warning в
  логи, не ошибка конфигурации.
- `backend/app/tasks/alerts.py` — периодическая Celery-задача
  (`alerts.check_health`, интервал `ALERTS_CHECK_INTERVAL_SECONDS`, по
  умолчанию 5 мин) на все четыре сигнала из задания:
  - источник недоступен дольше `ALERTS_SOURCE_UNAVAILABLE_MINUTES` —
    смотрит на `checks`: источник помечается как недоступный, только если
    **все** проверки по нему за окно — `source_unavailable`/`error` и хотя
    бы одна попытка была (нет попыток — нечего алертить, не ложное
    срабатывание на простое отсутствие заявок);
  - заявки застряли (`ALERTS_STUCK_APPLICATIONS_MINUTES`) — без смены
    статуса дольше порога, не в терминальном состоянии (то же определение,
    что `stuck_applications_over_1h` на экране состояния системы, T12, но
    порог отдельно настраиваемый для алертинга);
  - ответы заказчику не доходят — переиспользует существующий
    `PARTNER_OUTBOX_STUCK_MINUTES` (T18), отдельного ключа не заводил;
  - бэкап не сделан (`ALERTS_BACKUP_MAX_AGE_HOURS`) — по mtime маркера.

  Дедуп повторной отправки — в Redis (`SET NX EX`, та же техника, что
  `app/sources/throttle.py`), не чаще раза в
  `ALERTS_RESEND_INTERVAL_MINUTES` на один и тот же сигнал.
- `backend/app/config.py`, `backend/app/celery_app.py` — новые настройки и
  `check-health-alerts` в `beat_schedule`.
- `docs/deployment.md` — переписан в чек-лист: требования к серверу,
  переменные окружения (обязательные/необязательные), получение
  HTTPS-сертификата (certbot `--standalone` + инструкция по продлению),
  первый запуск, создание администратора (`python -m
  app.cli.create_admin`), бэкап/восстановление, оповещения в Telegram,
  обновление версии — плюс перенесены актуальные разделы из T11/T12/T13/T16
  (обратный прокси и `X-Forwarded-For`, один origin и CORS, DNS
  `statusnpd.nalog.ru`), устаревшие упоминания `PARTNER_BASE_URL`
  (до-T18 полевая схема) убраны.
- `.env.example` — добавлен блок «только для боя» (`DOMAIN`,
  `CERTBOT_CONFIG_DIR`, `BACKUP_*`, `TELEGRAM_*`).

## Проверено

- `pytest -q` (backend, в контейнере, после пересборки `api`/`worker`):
  **570 passed** (556 прежних + 14 новых в `tests/test_alerts.py` —
  источник недоступен/восстановлен, заявки застряли, outbox застрял, бэкап
  свежий/устаревший/отсутствует, дедуп в Redis, сам вызов Telegram через
  respx: отправка, пропуск без токена, устойчивость к 500 от Telegram).
- Синтаксис всех трёх shell-скриптов (`sh -n`).
- `docker compose -f docker-compose.prod.yml config` — структура валидна;
  без обязательных переменных падает с понятным сообщением (проверено
  намеренно, без единой переменной в окружении).
- `docker build -f frontend/Dockerfile.prod` — сборка статики проходит
  (`npm run build`, `tsc --noEmit` зелёный).
- `nginx -t` против реально отрендеренного шаблона (envsubst, с тестовым
  самоподписанным сертификатом) — конфиг синтаксически корректен.

**Не проверено живьём** (нет сервера заказчика и домена в этой сессии):
полный `docker compose -f docker-compose.prod.yml up` end-to-end с реальным
доменом/сертификатом/публичным доступом, фактическая доставка сообщения в
реальный Telegram-чат (respx проверяет только то, что мы шлём правильный
HTTP-запрос с правильным телом — не то, что настоящий Telegram API его
принимает так же), реальное восстановление из дампа на сервере заказчика.

## Допущения

- «Проверка восстановления на тестовой базе» реализована как отдельный
  скрипт для ручного/планового (например, недельного cron) запуска, не как
  часть автоматического ежедневного бэкапа — развёртывание дампа даже во
  временную базу занимает заметное время и ресурсы, гонять это каждый день
  вместе с самим бэкапом избыточно. Алертинг «бэкап не сделан» проверяет
  только факт дампа (маркер), не факт восстановимости — это разные гарантии,
  написано явно в комментарии скрипта.
- Сертификат — через `certbot --standalone` на хосте (не контейнеризованный
  ACME-webroot через nginx) — проще и не требует держать порт 80 занятым
  nginx во время самого первого выпуска; требует разовой ручной операции
  (`certbot renew` + перезапуск `nginx`) при продлении, задокументировано.
- Адрес `nginx` для `--forwarded-allow-ips` — фиксированная подсеть
  `172.28.0.0/24` со статическим IP контейнера, не маска всего docker-пула
  и не `*` (то же требование, что в T12) — единственный способ получить
  предсказуемый конкретный адрес без отдельного bridge-сетевого плагина.
