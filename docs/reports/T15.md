## 1. Формат выгрузки неизвестен — импорт через конфиг, идемпотентный пакет

**Что сделано:**
- `config/import_mappings/*.yaml` — соответствие «наше поле -> колонка CSV» для каждого из трёх видов импорта; формат выгрузки поменяется — поменяется конфиг, не код.
- `ImportBatch` (append-only): `file_sha256 UNIQUE`, исходные байты файла — через `Storage` (тот же механизм, что фото паспортов — ваше явное указание, см. раздел «мелочи» ниже), не инлайн в БД.
- Повторная загрузка того же файла (тот же хеш) возвращает существующий пакет, `created: false`, ничего не создаёт заново.

**Тесты:** `test_reimporting_same_contracts_file_does_not_duplicate` — два подряд одинаковых файла → один `ImportBatch`, один `Contract`.

## 2. Связь договора с заявкой — только по однозначному идентификатору, остальное — кандидат

**Ваше уточнение при подтверждении плана:** никакой автоматической привязки по телефону/ФИО. Автоматически — только номер заявки/договора из выгрузки. Совпадение по телефону/ФИО — кандидат в отчёте, подтверждает человек, с записью в аудит.

**Что сделано:**
- `contracts.application_id` — nullable. Автоматическая привязка — только если в строке CSV есть колонка `match_external_id` и её значение точно совпадает с `applications.external_id`.
- Если точного совпадения нет — договор всё равно импортируется (график/платежи не теряются), `application_id = NULL`, и для каждого найденного по телефону/ФИО клиента создаётся `ContractLinkCandidate` (`status="pending"`) — **не применяется автоматически**.
- `GET /api/imports/contract-candidates` — очередь на подтверждение; `POST .../confirm` — ставит `application_id`, пишет `audit_log` (`action="link_contract"`); `POST .../reject` — просто закрывает кандидата.
- Непривязанные договоры и число найденных кандидатов — в самом ответе загрузки (`unmatched_contracts`), видно сразу после загрузки, не только в отдельной очереди.

**Тесты:**
- `test_contract_import_matches_by_exact_external_id` — точный идентификатор → привязано автоматически.
- `test_contract_import_unmatched_creates_candidate_not_auto_linked` — телефон/ФИО совпали → НЕ привязано, создан кандидат.
- `test_confirm_contract_candidate_links_and_audits` — подтверждение привязывает и пишет аудит.

## 3. Неустойка — не платёж по графику

**Что сделано:** `payments.kind` (`regular | penalty | reversal`), из колонки `kind_map` в `config/import_mappings/payments.yaml`. Движок просрочки (`app.engine.delinquency`) получает на вход только `regular`/`reversal`-суммы — `penalty` туда не передаётся вовсе, только хранится (сырые данные).

**Тесты:** `test_payments_import_separates_penalty_and_applies_reversal` — платёж/неустойка/сторно в одном файле, в `delinquency_daily` неустойка не участвует.

## 4. Дни просрочки — самый старый взнос первым, частичные/переплата/досрочное, льготный срок из конфига

**Что сделано:**
- `app/engine/delinquency.py::allocate_payments` — классический waterfall: сумма зачтённых платежей на дату разносится по графику от самого старого периода к самому новому. Частичный платёж оставляет остаток на периоде; переплата/досрочное гасит следующие периоды; если денег не хватило — все последующие периоды остаются должными целиком.
- `grace_days` — `config/collections.yaml`, не хардкод. `days_past_due = max(0, (as_of - due_date самого старого непогашенного периода) - grace_days)`.
- Платежи по московскому календарю (ваше явное указание «мелочи») — все даты (`due_date`, `paid_at`, `as_of`) целиком завязаны на обычный `date`, конвертация нужна только для «сегодня» в ежедневной задаче: `app.engine.delinquency_recompute.moscow_today()` берёт дату по `Europe/Moscow`, не UTC.

**Тесты:** `test_synthetic_scenarios_exact_numbers` (параметризован 5 сценариями: вовремя, пропущенный взнос, частичный платёж, переплата/досрочное, сторно) — каждое число (`days_past_due`, `overdue_amount`) сверяется с заранее известным, не один агрегат.

## 5. Незрелые договоры — NULL, зрелость от даты данных, а не от сегодня

**Ваше уточнение при подтверждении плана:** окно наблюдения заканчивается датой, по которую есть данные (из пакета импорта платежей), а не текущим днём. Таргет известен в трёх случаях, иначе NULL: окно полностью покрыто данными; плохой исход уже наступил внутри окна; договор полностью погашен досрочно внутри окна.

**Что сделано:**
- `ImportBatch.data_as_of` — обязательное поле при загрузке платежей (форма на экране спрашивает дату явно).
- `target_bad_60_6` / `target_bad_90_12` (SQL-представления, не таблицы — ТЗ: «определение таргета будет меняться») реализуют ровно эти три случая (`CASE WHEN max_dpd_in_window >= порог THEN 1 WHEN closed_at <= конец_окна THEN 0 WHEN data_as_of >= конец_окна THEN 0 ELSE NULL END`) плюс `is_mature` рядом.
- Горизонт данных — `MAX(data_as_of)` по всем завершённым пакетам платежей (не по дате последнего импорта для КОНКРЕТНОГО договора — общий горизонт по всему потоку выгрузок).

**Тесты:** `test_target_views_three_known_cases_and_stale_data` — все три известных случая плюс контрольный «по календарю окно уже прошло, но данные только на 2 месяца вперёд — договор НЕЗРЕЛЫЙ», одним тестом на оба представления.

## 6. Исправления в учётной системе — без нарушения «ничего не перезаписываем»

**Ваше решение:** `delinquency_daily` — производные данные, перезапись разрешена (целиком вычислима из append-only `payments`). `computed_at` — для диагностики, не в ключе. Команда полного пересчёта + тест «полный пересчёт = накопленные ежедневные задачи».

**Что сделано:**
- `CLAUDE.md`, правило 1 — явное исключение добавлено текстом (по вашей формулировке).
- `payments` — append-only: отмена/исправление не UPDATE/DELETE исходной строки, а новая строка (`kind="reversal"`, `reverses_payment_id` на исходную, опционально).
- `delinquency_daily.computed_at` — обычная колонка, НЕ часть первичного ключа (PK остаётся `(contract_id, as_of)` по ТЗ).
- Ежедневная задача (`app/tasks/delinquency.py`) и команда полного пересчёта (`app/cli/recompute_delinquency.py`) — **буквально одна и та же функция** (`recompute_all_contracts`): каждый вызов пересчитывает всю историю договора от `issued_at` до текущей даты заново и перезаписывает (upsert) `delinquency_daily`. Это сознательное упрощение (документировано в коде): при текущем масштабе (ТЗ — «несколько десятков заявок в месяц») не проблема производительности, зато гейт «полный пересчёт = накопленные ежедневные» верен по построению, а не случайно, и исправление задним числом подхватывается автоматически на следующий тик, без отдельной логики «найти, что изменилось».

**Тесты:**
- `test_full_recompute_matches_accumulated_daily_runs` — 90 дней, вызов «ежедневно» день за днём против одного вызова с конечной датой → идентичные `delinquency_daily`.
- `test_backdated_correction_updates_past_days_on_next_recompute` — платёж с датой «вчера» добавлен сегодня → следующий пересчёт исправляет уже записанную прошлую строку; сам платёж при этом не редактировался (проверено: ровно одна строка `payments`).

## 7. Исторические заявки — с явной пометкой источника, включая отказников без договора

**Ваше уточнение «мелочи»:** исторические заявки без договора (отказанные) — тоже импортировать, если есть в выгрузке, для reject inference на этапе 2.

**Тест:** `test_historical_application_import_has_no_feature_snapshots`.

## Допущение, не покрытое буквально в ТЗ

ТЗ описывает импорт «договоров и платежей» как двух сущностей; график платежей (`payment_schedule`) явно не описан как третий импортируемый файл, а формат выгрузки договоров неизвестен заранее. Решил: график генерируется нами (равные ежемесячные платежи от даты выдачи на основе суммы/срока из самого договора), не импортируется отдельно — параметры рассрочки у нас и так есть. Если реальная выгрузка окажется с неравными платежами (например, аннуитет с какой-то другой логикой) — понадобится либо отдельный импорт графика, либо явная формула в конфиге; текущий код этого не предполагает.

# Правки после первой версии (раунд 2)

Четыре пункта из вашего сообщения после первого ревью — все про корректность
таргета и полноту данных. Ничего не закоммичено, как и раньше.

## 1. Закрытый договор — не всегда хороший (`closure_outcome`)

**Ваше замечание:** договор закрывается и при изъятии товара, и при списании
долга — это дефолт, не погашение. Таргет 0 должен ставиться только при полном
погашении; причина закрытия приходит в выгрузке, трактовка — в конфиге;
неизвестная причина — NULL, не 0.

**Что сделано:**
- Новые колонки на `contracts`: `closure_reason` (сырая причина из выгрузки,
  как есть, для аудита/прозрачности) и `closure_outcome` (`good | bad |
  unknown`, миграция `0015`/`0016` — ещё не закоммичены, поэтому правились на
  месте, не новой миграцией поверх, см. правило 9 CLAUDE.md про уже
  закоммиченные миграции).
- `config/import_mappings/contracts.yaml::closure_outcome_map` — трактовка
  строки причины закрытия в `good`/`bad`; отсутствие строки в карте при
  заполненном `closed_at` → `closure_outcome="unknown"` (не 0, не 1).
  Пороги/названия причин — в конфиге, не в коде (правило 2 CLAUDE.md).
- `target_bad_60_6`/`target_bad_90_12` (`alembic/versions/0016_target_views.py`)
  переписаны: порядок проверки в `CASE` —
  1. DPD ≥ порог внутри окна → `bad=1` (жёсткая улика важнее трактовки причины
     закрытия, даже если потом договор закрыли с хорошей причиной);
  2. закрыт до конца окна с `closure_outcome='good'` → `bad=0`;
  3. закрыт до конца окна с `closure_outcome='bad'` → `bad=1`, даже если 60/90
     дней просрочки по графику формально не набралось;
  4. закрыт до конца окна с `closure_outcome='unknown'` → `bad=NULL`,
     **навсегда**, пока причина не станет известна (не переходит в «0» даже
     если потом окно полностью покрывается данными — `is_mature` для этого
     случая тоже `false`, иначе были бы противоречивые «зрелый, но NULL»);
  5. иначе — окно полностью покрыто данными → `bad=0`;
  6. иначе — `NULL` (не зрело).

**Тесты (на каждую ветку, как и просили):**
`test_target_views_three_known_cases_and_stale_data` дополнен тремя новыми
сценариями вместо одного «закрыт»: `VIEW-CLOSED-GOOD` (погашен досрочно →
`(0, True)`), `VIEW-CLOSED-BAD` (товар изъят, **без единого дня просрочки по
графику** → `(1, True)`), `VIEW-CLOSED-UNKNOWN` (нераспознанная причина →
`(None, False)`). Плюс сквозной тест на реальном импорте:
`test_contract_import_classifies_closure_outcome_from_config`
(`test_api_imports.py`) — все три ветки через настоящий CSV и конфиг, не
напрямую через ORM.

## 2. График — импортом, генерация только запасным вариантом

**Ваше замечание:** добавить третий импорт — график платежей, со своим
маппингом колонок; если график по договору пришёл — используется он, если нет
— генерируется равными платежами с пометкой `schedule_source=generated`,
видной на карточке договора и в отчёте импорта.

Это одновременно снимает «Допущение, не покрытое буквально в ТЗ» из раунда 1
выше — график теперь полноценно импортируется, генерация осталась только
запасным путём.

**Что сделано:**
- `POST /api/imports/payment-schedule` — третий импорт, свой маппинг
  `config/import_mappings/payment_schedule.yaml` (`external_number, period_no,
  due_date, due_amount`), привязка по `external_number`, как и у платежей.
- `app/engine/imports.py::import_payment_schedule` группирует строки файла по
  договору и **заменяет** его график целиком (удаляет старые
  `PaymentSchedule`, вставляет новые) — `payment_schedule` не входит в
  append-only список правила 1 CLAUDE.md (это условие сделки, не факт-лог, в
  отличие от `payments`), поэтому полная замена допустима. Сопровождается
  `contract.schedule_source = "imported"`.
- `Contract.schedule_source` (`generated | imported`, колонка с
  `server_default='generated'` — существующие и ещё не тронутые договоры
  остаются с пометкой «сгенерирован» без доп. миграции данных).
- Видимость пометки: `ContractDetail` (API) и карточка договора (бейдж «из
  выгрузки» / «сгенерирован» рядом с заголовком «График платежей»); отчёт
  обоих импортов (`contracts`, `payment-schedule`) — через обычный
  `ImportResult`, ничего специального добавлять не пришлось.

**Тесты:**
- `test_payment_schedule_import_replaces_generated_schedule` — сгенерированный
  равный график (3×4000) заменяется неравным импортированным (2000/5000/5000),
  старые строки не остаются рядом с новыми, `schedule_source` переключается.
- `test_imported_schedule_produces_different_delinquency_than_generated` —
  **ваше явное требование**: один и тот же договор, один и тот же платёж,

## 1. 22 заявки зависли в статусе `ocr`

**Находка:** фоновая задача стадии А вызывает провайдера распознавания

моменту статус заявки уже закоммичен как `ocr` (переход записывается ДО

уровне ОДНОЙ заявки и продолжает цикл — но следующий тик выбирает заявки

больше никогда не попадает в выборку. Результат — тихое зависание навсегда,
безо всякого сигнала. Это прямое нарушение правила 4 CLAUDE.md (сбой
источника не должен останавливать заявку) — простое распространение на OCR,

## 3. Предупреждение о неполноте выгрузки — сверка по файлу договоров, не платежей
