# T18 — Интеграция по новой схеме: push вместо опроса

Заказчик сам шлёт нам заявки на наш API и сам же принимает наши ответы на свой
эндпоинт — вместо того, чтобы мы ходили к нему под служебным аккаунтом и
опрашивали его API по расписанию. Формат обоих направлений — наш (явно
разрешено заданием: «формат определяем мы»).

## Состав реализации

- `backend/app/api/partner_webhooks.py` — два входа: `POST /api/v1/partner/applications`
  (новая заявка с сайта), `POST /api/v1/partner/review` («Принять на рассмотрение»).
  Оба — `202` сразу, Celery-задача асинхронно дальше (OCR→стадия А / стадия Б).
  Токен в заголовке + опциональный allowlist IP (`verify_partner_webhook`).
  Идемпотентность — по `event_id` (`partner_inbound_events`, уникальный индекс),
  не по хешу содержимого и не по статусу заявки, как было раньше.
- `backend/app/integrations/partner_notifier.py` (новый, заменил `fake_partner_client.py`) —
  исходящий POST на один их эндпоинт (URL/токен из env), три вида события
  различаются полем `type` в теле (`ocr_result` | `decision` | `comment`).
  `409` с `{current_status, reason}` в теле → `PartnerConflictError` без
  отдельного запроса «а какой у вас статус» — значение уже в теле ответа.
  5xx/таймаут → `PartnerUnavailableError`, запись уходит в outbox, не теряется.
- `backend/app/models/partner_webhook.py` + миграция `0018` — `PartnerInboundEvent`
  (append-only, дедуп по `event_id`) и `PartnerOutboxEvent` (очередь гарантированной
  доставки: `pending → sent | conflict`, нарастающий `next_attempt_at`). Оба
  задокументированы в CLAUDE.md правило 1 как исключения/не-исключения —
  `partner_outbox_events` обновляется на месте как состояние очереди (как
  `bki_requests_in_flight`), `partner_inbound_events` — обычный факт-лог.
- `backend/app/tasks/partner_outbox.py` — периодическая Celery-задача
  (`partner_outbox.drain`, интервал `partner_outbox_sweep_interval_seconds`),
  повтор недоставленного с экспоненциальной задержкой
  (`partner_outbox_base_delay_seconds` → `partner_outbox_max_delay_seconds`).
- `backend/app/engine/pipeline.py`, `stage_b_pipeline.py` — `_write_back` теперь
  берёт ожидаемый текущий статус из `application.partner_last_known_status`
  (новое поле, пишется при каждом входящем вебхуке), а не из захардкоженной
  константы `"new"`/`"on_review"`. После успешного OCR — отдельный вызов
  `send_ocr_result(...)`, не дожидаясь решения стадии А.
- Удалено целиком: `app/integrations/fake_partner_client.py` (polling-клиент),
  `app/tasks/integration.py` (задача периодического опроса их API), связанный
  тест на `sync_applications`.
- `fake_partner/` переписан под новую схему: теперь это она шлёт нам вебхуки
  (`POST /_test/trigger-new-application`, `POST /_test/trigger-review/{external_id}`)
  и принимает наши ответы (`POST /partner/webhook`), вместо того чтобы отдавать
  данные по GET-запросам. Служебные эндпоинты для тестов: `/_test/received/{external_id}`
  (что мы прислали), `/_test/configure` (режим ok/conflict/unavailable),
  `/_test/manual-status/{external_id}`, `/_test/photos/{token}` (url-вариант фото).
- `scripts/e2e_check.py`, `scripts/_e2e_runner.py` — переписаны под вебхуки,
  убран мёртвый `"sync"`-таск.
- `docs/integration_contract.md` (новый) — человекочитаемый контракт с примерами
  JSON в обе стороны, для программистов заказчика.
- `docs/openapi.yaml` (новый) — машиночитаемая схема двух наших входов (формат
  их эндпоинта описан только текстом в контракте — это не наш сервис).
- `docs/spec.md` — раздел «Интеграция с системой заказчика» переписан под push
  (старое описание опроса/служебного аккаунта оставалось бы прямо противоречащим
  коду). DDL дополнен новыми таблицами. `CLAUDE.md` — обновлены вводное описание
  потока и правило 1 (новое исключение).
- `config/rulesets/dev.yaml` — `stage_b_completeness.required_sections`: убран
  `address` (см. «Допущения» ниже).

## Допущения, принятые в рамках «формат определяем мы»

1. **В `/review` добавлена секция `employment`**, хотя её не было в перечне
   полей задания. Без неё `stage_b_completeness` систематически не пропускал бы
   анкету дальше — ПДН и часть правил стадии Б используют тип занятости, это
   не опционально для работы скоринга, а не «добавили заодно».
2. **Из `stage_b_completeness.required_sections` убран `address`.** В задании
   его тоже не было в перечне полей `/review`, и по факту адрес регистрации уже
   приходит через OCR на стадии А (паспорт с пропиской) — требовать его ещё раз
   отдельной секцией анкеты избыточно.

Оба пункта — решения в рамках явно данной свободы по формату, не молчаливое
расширение задания; выношу отдельно, чтобы вы могли поправить, если видите
иначе.

## Что осталось открытым

- **`git push origin main` заблокирован автоматической классификацией
  Claude Code** («dangerous»/исходящее действие) — не обходил эту блокировку,
  коммит сделан локально. Нужно либо запушить вручную, либо явно разрешить
  `git push` в разрешениях сессии.
- Реальный URL/токен системы заказчика (`PARTNER_OUTBOUND_URL`/`PARTNER_OUTBOUND_TOKEN`,
  `PARTNER_INBOUND_TOKEN`) — в `.env.example` только плейсхолдеры, боевые
  значения подставляются при развёртывании (см. T19/`docs/deployment.md`).
  Аналогично allowlist IP (`PARTNER_IP_ALLOWLIST`) — пуст по умолчанию, не
  проверяется, пока вы не пришлёте список адресов заказчика.
- Протокол `409` на их эндпоинте («верните текущий статус») — обязанность
  СОБСТВЕННО их API, их стороне нужно уметь так ответить. Проверить это до
  интеграции с настоящей системой нельзя, только с `fake_partner`, которая
  это умеет по команде `/_test/configure`.
