# Импорт договоров/графиков/платежей и допущение о полноте выгрузки

Три независимых импорта (ТЗ «Договоры и платежи», T15), каждый со своим
маппингом колонок в `config/import_mappings/` — формат выгрузки из учётной
системы заказчика заранее не известен, код импортёра (`app/engine/imports.py`)
не содержит реальных названий колонок:

| Импорт | Эндпоинт | Маппинг | Что делает |
| --- | --- | --- | --- |
| Договоры | `POST /api/imports/contracts` | `config/import_mappings/contracts.yaml` | создаёт/обновляет `contracts`, генерирует равный график (запасной вариант), классифицирует причину закрытия (`closure_outcome`) |
| График платежей | `POST /api/imports/payment-schedule` | `config/import_mappings/payment_schedule.yaml` | заменяет сгенерированный график реальным, если он пришёл отдельным файлом; ставит `schedule_source = imported` |
| Платежи | `POST /api/imports/payments` | `config/import_mappings/payments.yaml` | добавляет строки в `payments` (append-only, правило 1 CLAUDE.md) |

Каждый импорт идемпотентен по SHA-256 файла (`import_batches.file_sha256
UNIQUE`) — повторная загрузка того же файла не создаёт дублей.

## Допущение: каждая выгрузка платежей полна по всем действующим договорам

Общий горизонт данных (`data_horizon`, используется `target_bad_60_6` /
`target_bad_90_12` и `app/engine/delinquency_recompute.py`) считается как
`MAX(import_batches.data_as_of)` по всем завершённым пакетам `kind='payments'`
— **не** по максимальной дате платежа внутри пакета, а по дате, на которую
выгрузка **в целом** актуальна (поле `data_as_of`, которое заказчик указывает
при загрузке).

Это верно только при допущении: **каждая выгрузка платежей, которую заказчик
отдаёт, содержит все платежи по всем действующим на тот момент договорам**, а
не только по какому-то подмножеству (например, только по договорам одного
региона или одной продуктовой линейки). Если выгрузка частична, но её
`data_as_of` выставлена как обычно, `data_horizon` для **не попавших** в неё
договоров окажется завышенным — они будут считаться наблюдаемыми вплоть до
этой даты, хотя по ним фактически нет данных о платежах за этот период, и
`is_mature`/`bad` для таких договоров может ошибочно показать «просрочки нет»
вместо «данных нет».

### Почему проверка не по файлу платежей

Первая версия этого предупреждения сверяла файл платежей сам с собой: если
действующий договор не встретился ни в одной строке файла — предупреждение.
Это оказалось неверно: у договора, который действующий, но просто **не
платит** (тот самый просрочник, ради которого вся система и существует),
строк в файле платежей закономерно нет вовсе — не потому что выгрузка
неполная, а потому что платить ему нечем. Предупреждение срабатывало бы
ровно на самых рискованных договорах, и оператор быстро научился бы его
игнорировать (стандартный сценарий «усталости от алертов»).

### Как проверяется на самом деле

Полнота выгрузки платежей проверяется **не по ней самой**, а по отдельной
выгрузке ДОГОВОРОВ, сопоставленной по дате: при загрузке `payments.csv`
указывается `data_as_of` (как и раньше); если среди пакетов `kind='contracts'`
есть завершённый пакет с **такой же** `data_as_of`, его содержимое (список
`external_number` в файле договоров, не в самой БД) и берётся эталоном.
Предупреждение — только если действующий (`status='active'`) договор
отсутствует в этой сопоставленной выгрузке договоров: это означает, что сама
учётная система заказчика на эту дату уже не считает его частью выгрузки
(закрыла, передала в другую систему и т.п.), что система видит неполностью —
а не что по нему просто не было платежей в периоде.

Выгрузка договоров поэтому теперь тоже необязательно принимает `data_as_of`
(`POST /api/imports/contracts`) и поддерживает повторную загрузку: уже
известный `external_number` при повторной выгрузке **обновляет** существующий
договор (статус, закрытие, суммы), а не создаёт дубликат — периодическая
выгрузка договоров описывает текущее состояние на дату, а не разовый факт
(`contracts` не входит в append-only список правила 1 CLAUDE.md).

**Если выгрузки договоров с такой же датой нет** (например, договоры
загружались один раз без даты, а платежи — периодически), сверить не с чем —
предупреждение не выдаётся вовсе, список пуст. Чтобы предупреждение
действительно работало, оператору нужно загружать выгрузку договоров той же
датой, что и соответствующую выгрузку платежей — это операционное требование,
не автоматически проверяемое системой.

### Как это проявляется в отчёте импорта

`POST /api/imports/payments` возвращает `missing_active_contracts` — список
`external_number` действующих договоров, отсутствующих в сопоставленной по
дате выгрузке договоров. Непустой список — предупреждение, не ошибка (файл
платежей всё равно импортируется): «N действующих договоров отсутствуют в
этой выгрузке». Отображается на экране «Импорт данных»
(`frontend/src/pages/Imports.tsx`) рядом с остальным отчётом по пакету.

Предупреждение не проверяет *корректность* дат внутри уже присутствующих в
выгрузке договоров строк — только полное отсутствие договора в ней. Если сама
выгрузка договоров тоже систематически теряет часть действующих договоров (а
не только выгрузка платежей), предупреждение это всё равно поймает — ровно
для этого оно и сверяется с отдельной, независимо формируемой выгрузкой, а не
с тем, что уже есть в нашей БД.
