# Часть 1. Для людей

## Что это

DIALOG Scoring — сервис, который помогает решать, давать ли клиенту исламскую
рассрочку (мурабаха) на товар. Он работает рядом с CRM компании: CRM ведёт
клиентов и сделки, а наш сервис проверяет клиента и говорит «одобрить»,
«отказать» или «пусть решит человек».

У сервиса есть **админка** — сайт для сотрудников, где видно каждую заявку,
все проверки, решение и почему оно такое.

## Как заявка проходит через систему

1. **Клиент оставляет заявку на сайте.** CRM присылает нам ФИО, телефон и два
   фото паспорта (разворот и прописка).
2. **Стадия А — бесплатные проверки, сразу.**
   - Распознаём паспорт с фото (данные уходят обратно в CRM).
   - Проверяем паспорт на ошибки (формат, срок, дата выдачи, код подразделения,
     не встречался ли у другого человека).
   - Сверяем с перечнем террористов и экстремистов Росфинмониторинга и с нашим
     чёрным списком; проверяем возраст.
   - В фоне ищем ИНН и статус самозанятого в ФНС.
   - Итог: **отказ** (если явный стоп-фактор) или **«передать оператору»** —
     оператор CRM звонит клиенту. Одобрения на этой стадии не бывает.
3. **Оператор CRM звонит и нажимает «Рассмотреть».** CRM присылает анкету:
   товар, цену, взнос, срок, доход, платежи по другим кредитам, согласие на
   запрос кредитной истории, поручителя.
4. **Стадия Б.**
   - Дешёвые проверки: разрешён ли товар по шариату, укладывается ли сделка в
     лимиты тарифов, не слишком ли большая долговая нагрузка по словам клиента.
   - **Кредитная история — только по кнопке.** Запрос в бюро платный, поэтому
     система останавливается и ждёт: сотрудник в карточке нажимает
     «Обычный отчёт» (кредитный рейтинг — обычно его хватает) или
     «Подробный отчёт» (дороже, нужен редко). Если отчёт не пришёл, кнопки
     остаются — можно запросить ещё раз.
   - По отчёту: балл, долговая нагрузка, просрочки → **одобрено**, **отказ**
     или **серая зона** (решает оператор CRM).
5. **Ручные проверки сотрудников.** ФССП (долги у приставов — сотрудник вводит
   код с картинки) и банкротство (сайт Федресурса, сотрудник смотрит и
   отмечает). Без проверки ФССП система не одобрит — только серая зона.
6. **Решение уходит в CRM** — статус, балл и причина обычным текстом.

## Что есть в админке

| Раздел | Зачем |
| --- | --- |
| **Заявки** | Список и карточка заявки. Вверху — клиент, решение, кнопки, главные цифры (балл, долговая нагрузка, платёж, рейтинг клиента) и путь заявки. Ниже — запрос кредитной истории, ручные проверки, рейтинг клиента, ход заявки; анкета и данные — свёрнуто внизу. |
| **Перечни** | Совпадения клиентов с перечнем Росфинмониторинга: сотрудник проверяет, он ли это, и снимает заморозку или подтверждает. |
| **Скоринг** | Правила и пороги (возраст, лимиты, долговая нагрузка, пороги балла…). Можно поменять, проверить на прошлых заявках и опубликовать новую версию; каждая версия сохраняется. |
| **Аналитика** | Сколько заявок, сколько одобрено и отказано, причины отказов, распределение баллов, работа источников. |
| **Портфель → Клиенты** | Клиенты и их заявки. |
| **Справка** | Как пользоваться, термины. |
| **Настройки** | Сотрудники, справочники (чёрный список), журнал аудита, состояние системы. |

**Роли сотрудников:** администратор (всё), оператор (ФССП, банкротство,
перечни, запрос кредитной истории), наблюдатель (только просмотр). Персональные
данные видят все роли, каждый просмотр записывается в журнал.

**Рейтинг клиента** — баллы по критериям заказчика (возраст, контакты, работа,
прописка). Пока только для информации, на решение не влияет.

**Анализ ИИ** и кнопки «Принять / Отказать» — заготовки, в разработке.

## С чем система связана

| Что | Как |
| --- | --- |
| CRM | По их API: они шлют нам заявки и анкеты, мы им — распознанный паспорт и решения. Если CRM недоступна — досылаем позже, ничего не теряется. |
| Кредитная история | Спектрум Дата — пакеты «Кредитный рейтинг» (обычный) и «Проверка соискателя — Премиум» (подробный). Подключено по их API, доступ проверен (02.11.2026). |
| Перечень террористов и экстремистов | Раз в сутки с открытой страницы Росфинмониторинга (нужен российский IP). |
| ФССП | Сайт ФССП, сотрудник вводит код с картинки. |
| Банкротство | Сайт Федресурса, сотрудник проверяет сам — сайт закрыт от автоматических запросов, обходить защиту мы не стали. |
| ФНС | ИНН, самозанятость, ИП — автоматически в фоне. |
| Распознавание паспорта | Claude по API-ключу. |

## Что важно знать

- Система ничего не стирает: каждое решение, проверка и смена статуса
  сохраняются навсегда — видно, кто и что делал и почему.
- Пороги и правила меняются в «Скоринге», без программиста.
- Если внешний источник недоступен, заявка не отклоняется автоматически, а
  уходит человеку.
- Пароли, ключи и токены хранятся только в файле `.env` на сервере.

## Что ещё не сделано

- Кредитная история (Спектрум Дата): подключена, проверена на демо-клиенте
  («нет данных»); осталась проверка на реальном человеке с согласием.
- Со стороны CRM: адрес их API и токены (CRM будет на том же сервере),
  паспорт поручителя в анкете.
- Передача решения сотрудника («Принять / Отказать») в CRM, анализ ИИ.
- Установка на боевой сервер — по `docs/deployment.md`.

# Часть 2. Для Claude

Сначала прочитай `CLAUDE.md` — там непреложные правила (append-only таблицы,
бизнес-логика только в YAML, без ПД в логах, секреты только в env, миграции
только новые, тесты без сети). Этот раздел — карта проекта поверх него.

## Стек и сервисы

Python 3.12 · FastAPI · SQLAlchemy 2 async · Alembic · PostgreSQL 16 · Celery +
Redis · httpx · Pydantic v2 · structlog. Админка — React + Vite + TypeScript
(`frontend/`), типы API генерируются из OpenAPI (`npm run gen:api`).

`docker-compose.yml` (dev): `db`, `redis`, `api` (FastAPI, :8000), `worker`
(Celery), `beat` (расписание), `frontend` (Vite, :5173), `fake_partner`
(заглушка CRM). Прод — `docker-compose.prod.yml` + `deploy/nginx`,
инструкция — `docs/deployment.md`.

**Код backend запечён в образ** — после правок бэкенда:
`docker compose up -d --build api worker beat`. Для быстрых проверок можно
`docker compose cp backend/app/. api:/app/app/` (только api, до пересборки).
Vite в Docker на Windows не видит изменений — `docker compose restart frontend`.

## Статусы заявки

`received → ocr → stage_a → rejected_a | to_operator` (стадия А);
`to_operator → stage_b → awaiting_bki → stage_b → approved | rejected_b | gray_zone`
(стадия Б). Также `ocr_failed`, `awaiting_data` (распознавание выключено —
паспорт ждём от CRM), `contracted`, `expired`. Переходы — только через
`engine/state_machine.transition` (пишет `status_history`).

## Интеграция с CRM (их API — `docs/crm_api.yml`)

- Вход (`api/partner_webhooks.py`, префикс `/api/v1/crm`, Bearer
  `PARTNER_INBOUND_TOKEN`, allowlist IP в проде):
  - `POST /new-order` — `orderId`, ФИО, телефон, `passportPhotos` [разворот,
    прописка] (base64 или https). Идемпотентно по `orderId` (`external_id` = str(orderId)).
  - `POST /scoring` — анкета; переводится во внутренний снимок
    `external_snapshots(stage="B").payload_raw.stage_b` (+ `crm_raw`). Тот же
    запрос повторно — ничего; изменённый — новая стадия Б. Необязательные
    расширения сверх их схемы: `employment`, `contacts`, `applicant`, `goodsName`,
    `tariff`, `monthlyPayment`, паспорт поручителя.
- Выход (`integrations/partner_notifier.py`, база `PARTNER_OUTBOUND_URL`):
  `/v1/integration/scoring/passport-result` и `/v1/integration/scoring/result`
  (`orderId, status, score, reason`). Неудача — `partner_outbox_events`,
  повтор задачей `partner_outbox.drain`. 409 с `current_status` (на будущее) →
  `manual_overrides`.
- Занятость не обязательна (`stage_b_completeness`), тарифа CRM не шлёт —
  считаем по `default_tariff` (решения владельца 02.11.2026; раньше без тарифа
  был отказ `UNKNOWN_TARIFF`). `PARTNER_IP_ALLOWLIST` понимает подсети — CRM
  может стоять на том же сервере.
- Решение оператора CRM (`manual_overrides`) по последнему решению системы —
  сверху карточки, его цветом; решение системы — строкой ниже. Кнопки
  «Принять / Отказать» — серые, «пока недоступно».

## БКИ

- `BKI_REQUEST_MODE=manual` (по умолчанию): `finalize_stage_b` без заказа
  переводит заявку в `awaiting_bki` и выходит. Кнопка → `POST
  /api/applications/{id}/bki-request {report_type}` → `bki_request_orders` +
  аудит → задача `stage_b.request_bki_report` → `finalize_stage_b` с заказом.
  Повтор, если отчёт не получен (`gray_zone` с `BKI_NOT_CONFIGURED |
  BKI_SOURCE_UNAVAILABLE | BKI_ERROR | BKI_CLIENT_UNKNOWN`): `gray_zone →
  awaiting_bki`. `auto` — без кнопок (тесты через conftest, демо-сид).
- Виды отчёта — `bki.report_types` в правилах (`label`, `provider_code` —
  идентификатор пакета у бюро, `allows_approval`); `bki.range_bound` — граница
  диапазонов.
- Провайдер: `BKI_PROVIDER_MODE` = `not_configured` | `fake` | `spectrum`.
  Спектрум Дата: разбор — `sources/spectrum.py` (P.0191 и блоки «Премиума» в
  `BUREAU_BLOCKS`), HTTP — `sources/spectrum_http.py` (AR-REST, `_make` →
  опрос, uid заказа в Redis — без двойного списания), проверка доступа —
  `python -m app.cli.spectrum check|report-types`. uid пакетов — в
  `bki.report_types.*.provider_code`. Проверки подробного пакета —
  `bki_bureau_checks` (в решение не входят). Тесты всегда с
  `BKI_PROVIDER_MODE=not_configured` (conftest). Подробно — `docs/bki_spectrum.md`.
- Кэш отчёта по клиенту (`bki.cache_days`), защита от двойной оплаты —
  `bki_requests_in_flight`.

## Ручные проверки

- ФССП (`api/fssp.py`, `sources/fssp.py`): is.fssp.gov.ru, капчу вводит человек,
  состояние диалога — `fssp_captcha_sessions`. `FSSP_SOURCE_MODE=http` —
  настоящий сайт.
- Банкротство (`api/fedresurs.py`): сотрудник открывает поиск на Федресурсе
  (ссылка с ИНН/ФИО) и отмечает результат. Автоматизировать нельзя (Qrator, не
  обходим).
- Поручитель: текущий — последний записанный (`engine/guarantors.py`); тот же
  человек в повторной анкете — та же строка (проверки сохраняются).

## Реестры

- Перечень Т/Э: `ROSFINMON_SOURCE=fedsfm_page` — ежедневно со страницы
  fedsfm.ru (нужен российский IP; 403 — сбой, старый перечень остаётся).
  Вручную: `docker compose exec worker python -m app.cli.sync_rosfinmon --dry-run`.
- МВД (недействительные паспорта) — реестр закрыт с 2023, в карточке не показываем.

## Скрытое в UI (решения владельца)

Договоры и импорт (учёт договоров ведёт CRM), настройка распознавания —
убраны из меню, страницы остались по прямому адресу. Тексты UI называют
внешнюю систему «CRM», не «заказчик».

## Как проверять

```bash
docker compose exec -T api pytest -q                           # backend
docker compose exec -T fake_partner python -m pytest -q tests  # заглушка CRM
cd frontend && npx tsc --noEmit -p . && npx playwright test    # админка (e2e, своя база)
```

Демо-данные: dev-база пустая → `docker compose stop worker beat`,
`seed_demo --password "$DEMO_SEED_PASSWORD" --showcase` (пароль из `.env`, в
контейнер передать через `docker compose exec -e DEMO_SEED_PASSWORD`),
`docker compose start worker beat`. Полный сброс dev-базы: `DROP SCHEMA public
CASCADE; CREATE SCHEMA public;` → `alembic upgrade head` → сид. Перед сбросом
сохранить строку владельца из `employees` (COPY) и вернуть после.

## Как работать с владельцем

- Пишет по-русски, неформально; отвечать коротко, по делу, без жаргона.
- Перед архитектурными решениями — спросить (CLAUDE.md, «Как работать»).
- Не коммитить `.env`, не выводить токены и пароли, не вводить чужие пароли,
  не обходить капчи и защиту сайтов.
- `git push` делает владелец сам (`git push origin main`).
- Заметные изменения UI — показывать скриншотом (временный Playwright-спек в
  `frontend/e2e/zz-*.spec.ts`, потом удалить).
